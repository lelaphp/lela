---
name: build
description: Build one ticket to its acceptance criteria and close it at the tracker. `/build <n>`; with no number, the branch's ticket.
disable-model-invocation: true
---

A ticket is finished when its branch is ready to merge. `xtask track work` reads one signal back from a session, the branch's ready record, and a session that ends any other way leaves its worktree standing for a person however green the work is. The ticket closes at the merge into `main`, which /specs makes and whose hook closes it (#2270): a closed ticket means its work is on `main`. So the ready record is the last act, and everything below is what earns it.

**Where you stand.** `cargo xtask ticket read <n>` prints the ticket's acceptance criteria and holds the work to them; without a number it reads the branch's. `gh issue view <n>` is the body and the blocking edges. `AGENTS.md` is the map and binds: read it and `CONTEXT.md` before the first edit, and read the ADR before touching what it names. `cargo xtask track` says the branch, the ticket it records and what `done` measures since, the merge base with `main`. The ticket's track is its `track:` label, or `main` where it carries none (ADR-0009).

**Checkout preflight.** Before implementation in the actual allocated checkout:

- Confirm its absolute path, branch, source head, recorded ticket and exclusive file ownership; reconcile existing edits and active owners before writing.
- Exercise the normal region renderer and `computed check` there before expensive work. Separate stale regions the renderer can refresh from an untrusted checkout or renderer failure. A trust grant remains a person's; wire that blocker before starting dependent work.
- Verify the pinned oracle and the task's required corpus provenance, libraries and runner access. Establish budget headroom and disk space with the existing instruments and readings; stop new large builds below /specs' disk floor.
- Read existing blockers and apply “Whether it is still to do” below at that head; reuse only matching evidence.

Record the checkout/head, evidence and concrete blockers in the handoff material. Complete independent work while a wired external blocker waits; keep blocked criteria honest. Preflight is a small examination of this task's prerequisites, not a broad validation run or authority to provision trust, credentials or protected files.

**Whether it is still to do.** Before the first edit, measure the ticket against the tip you were laid down at: run what its "what happened" ran, the probe under the engine and under the oracle, the named test, the grep, and read each box against what you see. A ticket whose behaviour already holds is answered under another number; its ending is the withdrawal below with that measurement as the reason, or, where every box holds, the close. Where some boxes hold and others do not, build only what does not. The oldest ticket is the first `track next` names and the likeliest to be answered already.

**The work.** The witness is the test: write the `php` fence beside the kernel or native before the body where you can, pin it with `cargo xtask witness --accept`, and read what it pinned rather than authoring an `exit=`. Copy php's algorithm where the behaviour is observable; where it is not, pick the smallest model. The smallest proof is the instrument for the crate you touched, `cargo xtask test --crate xtask` for the harness itself, and the commit's own hook is the measurement that counts: stage-commit's step 4 says what not to run twice. A difference from the oracle the engine is right about is a row proposed in the commit message, never written into `docs/divergence.toml`.

**Landing.** Land through `.claude/skills/stage-commit`, which is the order and the message shape: one concern, the instruments green, and staging by pathspec, `git add -- <paths>` and `git commit -F <file> -- <paths>`. The index is shared with every session in the checkout, so `git add -A`, `git add .` and a commit naming no path take what another session staged. `--no-verify` is not available to you.

**What you found is verified, then built or filed.** Found work is what you met that this ticket did not ask for. Your handback carries it in a fixed `## Found work` section, one item per line, and `None.` when it is empty. A person's act or a blocker is filed at once, as below, and its line names the ticket; every other item waits for the verifier. At source final, the sources finished and before `ticket ready`, a section with an item is verified: spawn one agent of the `advisor` role, the verifier, with a prompt carrying your handback, the worktree, its head and the section. It reads each item at that head, checks the tracker, and gives each one outcome with a citation: a file and line, a command and its output, or a ticket. It may run the worktree's built binary and the oracle; it edits, files, spawns and builds nothing, and an item it cannot check without a build ends as `file`, the ticket saying it was not probed. Where your brief asks for a second verifier on another model, spawn it beside the first with the same prompt, act on the advisor's outcomes, and name in the handback each item the two disagree on. Each item then ends as its outcome says:

- `absorb`: the ticket cannot pass without it, so it is this ticket's work and not found work. Do it before the ready record.
- `build`: it lies on the paths you own, needs no person's act and no lock or ceiling growth the ticket did not already need, and the verifier states its size. Add it to this ticket as a box, `gh issue edit <n> --body-file`, every existing box's text unchanged, and hand back with no ready record, saying the box waits on a fresh builder. One fresh builder builds it in the same worktree, and it is the only one a ticket gets: a fresh builder carries the verified lines it was handed into its own file, and files its own found work unverified, each item `file` or `person`, never `build`.
- `file`: a ticket of its own, filed as the next paragraph says.
- `person`: a `for-a-person` ticket, filed at once.
- `refuted`: the claim does not hold at this head, and nothing is filed.
- `noted`: it is true and there is nothing to do; the ready reading keeps its text.

Write the verified section to a file in your scratch directory, each line opening with its outcome and, for `file` and `person`, the ticket it was filed as: `file #<m>: <the item>, <the citation>`. That file is what `ticket ready --found` reads.

**What you file.** A ticket is `gh issue create`: `ready-for-agent` when an agent may take it, `for-a-person` when the act is a person's alone (harness-design.md §11), carrying the ticket's `track:` label when it has one, and no parent, since a chart takes no sub-issues, in the house shape — `## What to build`, `## Acceptance criteria` as boxes, `## Blocked by`. Search before you file: `gh issue list --state open --search "<the construct, native or test>"`, and where an open ticket already covers what you found, add it to that ticket, a comment or a box, rather than file a second, and name that ticket on the item's line. A subset's failures are filed one ticket per cause, naming every test the cause explains, never one ticket per failing test. A rule you want, or a divergence you found, is a paragraph in the commit message proposing it, with the fixture that would fail. Naming it in your reply alone does not file it.

**Ready to merge.** Walk `cargo xtask done` and say which entries applied. Tick every acceptance box the work meets, `gh issue edit <n> --body-file`, the box text unchanged; a box the work does not meet is work still to do, so go back. Then `cargo xtask ticket ready <n>`, with `--opens <m>` once per ticket this work filed, or `--opens-nothing` when it filed none, and `--found <file>` naming the verified section, or `--found-nothing` when the section is `None.`. That instrument is a builder's hold: it runs `done` over this worktree and refuses, naming the list, while anything the builder owns is unmet, the lanes the merge check owns being delegated in a ticketed worktree. It refuses a found file naming a filed ticket that `--opens` does not, and its reading counts the items by outcome. Accepted, it reads the ticket again, holds the successors and records the ticket ready on the branch, `branch.<name>.ready-<n>`, one record per ticket, so each ticket of a bundle is readied on its own; it closes nothing. A builder never meets the Stop hook: `SubagentStop` runs the same `done` as its turn ends and warns with the list, and `ticket ready` accepted is what earns the record. The merge into `main` closes the ticket with those successors, through `xtask ticket close`, which refuses a close of work done that `main` does not contain. `gh issue close` and `gh api ... state=closed` are denied to you, and that denial is the rule, not an obstacle: the close is the instrument that read the criteria, and nothing else closes a ticket.

**When `done` will not go green.** Do not force it and do not narrow the ticket to fit. If what blocks you is outside this ticket — a red reading you inherited, a manifest row or an oracle pin only a person may write, a decision the design of record does not make — file that blocker as a ticket, wire it on with `gh issue edit <blocker> --add-blocking <n>`, name its number in your reply, and leave this ticket open. `ticket ready` refuses and `SubagentStop` warns with the list; `track work` then leaves the worktree standing for a person, and the run goes on. That is the ending, not a defect to route around. The wired blocker is also how the merge reads a partial landing: when the branch merges with this ticket open, its subject names the ticket as any other, and the merge's hook leaves a ticket with no ready record, a box unticked and an open blocker open, saying so, where it would otherwise name it as unready (#2394). So the blocker is wired before the branch is handed on, and no ready record is written for this ticket.

**When the ticket describes nothing in the tree.** A ticket whose "what happened" is not what `main`'s tip does — the defect fixed under another number, the file gone, the measurement no longer reproducing — has a third ending, neither done nor blocked: `cargo xtask ticket close <n> --withdrawn "<what was run, on which commit, and what it showed>"`, with `--opens <m>` or `--opens-nothing` as any close. The instrument refuses it while any box is ticked, so a withdrawal is never a ticket narrowed to fit or a box ticked for work not done; it is the measurement that found nothing to build, recorded as the ticket's reason.
