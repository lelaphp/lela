# Conflicts that recur

Read when a merge in `_merge` conflicts, when the build or the hook refuses a merge that git took cleanly, or when `land` refuses one. Merges are made on `staging` (SKILL.md, step 5), so `--ours` is `staging`, main's tip with the batch's merges before this one, and `--theirs` is the branch.

## The ones git shows

- **`AGENTS.md`** conflicts only in computed regions. Take `staging`'s side and re-render: `git checkout --ours -- AGENTS.md && cargo xtask regions AGENTS.md && git add -- AGENTS.md`.
- **A lock** (`heap.lock`, `api.lock`) where both sides added items. The resolution is the union in sorted order; `cargo xtask api-check` confirms it, and a count past `api_items` is a person's (SKILL.md, step 6).
- **A design ledger** (`harness-design.md`, `third-engine-design.md`, `jit-design.md`). A branch writes each revision it adds as `**NEXT. Revision NEXT (<date>).**`, `NEXT-2` for a second in one file, and cites it as `revision NEXT` in the sections it changes, since two branches that both took the next number conflicted at every merge (#2982). The merge numbers them: in the merged file, replace each `NEXT` (and `NEXT-2`) of the branch, the ledger row and each citation, with the next free revision after `staging`'s last, in order. Pre-commit refuses a commit on `main` or `staging` whose changed Markdown or Rust still cites a revision as `NEXT`, the row or a citation such as `revisions 11 and NEXT`, naming each line.
- **`Cargo.lock`**: take `staging`'s side, `git checkout --ours -- Cargo.lock`, and let `cargo build -p php_sapi_cli -p php_sapi_cgi` add only what's missing. A fresh `cargo generate-lockfile` moves every dependency the branch never asked to move.

## The ones the build or the hook shows

Git merges these cleanly and the result doesn't build, or builds and fails a witness.

- **A struct gained a field** on one side, and literals written on the other lack it (`Parameter::prefer_ref`, which ext/standard's `stub.rs` and ext/ctype's literals lacked). Add the field at every literal, with the value the branch that added it gives the neutral case.
- **An enum variant gained a field** (`Link::Frame`'s stack), and matches written on the other side don't bind it. Bind it at each match, and read what the new field means there before choosing `..`.
- **A harness file both sides changed** (`seams.toml`, `oracle.toml`, `docs/divergence.toml`), as when `staging` carries a person's `seams.toml` commit and the branch a steered row. Pre-commit, or pre-merge-commit for a merge git commits itself, refuses an agent's merge naming the file and #3644, even where git merged it cleanly, since the merge's content is neither side's commit; a refused pre-merge-commit leaves the merge standing, `MERGE_HEAD` and the staged file with it. While the merge stands, copy the merged file to your scratchpad and write it back through steer, `cargo xtask steer seams.toml --from <copy>`, which judges a merge in progress against the union of what each side carries over the merge base (#3633) and stamps its reading over that blob; then `git add -- seams.toml` and `git commit`. Where git conflicted, the copy is the resolved union you wrote; where it merged cleanly, the copy is the working file as git left it, and steer reads the three sides from the merge base, `HEAD` and `MERGE_HEAD` and holds the copy to the text `git merge-file` gives of them too (#4441), so edit nothing in it. The reading says what `HEAD` carries and what `MERGE_HEAD` brings, which may be nothing where `MERGE_HEAD` changed only comments, and still covers the merge. Steer writes nothing, and the merge waits on a person, where the two sides changed one value differently, where the copy changes, drops or adds anything neither side carries over the base, where the staged text is not what `git merge-file` gives of the three files, as a merge taken with `-X ours` or `-X theirs` leaves it where those files conflict, and in a criss-cross merge whose `HEAD` and `MERGE_HEAD` have several merge bases, which git merges over a base no commit carries. Two things it does not judge, both open on #4486: a change one side made over the base, a value changed or a row dropped, is read as settled where that side landed and is part of the union, whoever made that side's commit; and a file the merge leaves equal to `MERGE_HEAD`'s whole, as `-X theirs` can leave it, is read as that side's commit, which pre-commit does not ask steer to cover.
- **Two branches encoding one state two ways**, as `fe_pos` was between #681's hash iterators and #658's foreach over a Traversable. Resolve to one typed representation that serves both, never a third encoding beside the two: the standard in [builder-prompt.md](builder-prompt.md) holds a merge as it holds a builder.

## The ones the land shows

`cargo xtask worktree land` runs in main's checkout and is refused anywhere else. Its judges are an xtask built at main's tip, once per tip under main's `target/judge/` (#4372), never the xtask `_merge` builds, which is the merge's own: `budget`, `api-check` and `unsafe-audit` over `_merge`'s tree, steer over each harness file the batch changed, `cargo deny` where `Cargo.lock` moved, then `done`, with `permit --diff` inside it.

- **A harness file main's xtask cannot read.** A branch that adds a table or a key to `seams.toml`, `oracle.toml` or `docs/divergence.toml` that main's reader does not know yet is refused at the land, naming the file, the key and the two steps. A change to the grammar lands in two steps: first the xtask that reads the new grammar, merged and landed with no row that uses it; then, once main's tip carries that xtask, the row that uses it, in a batch of its own. Take the row's merge back out of `staging` (`git reset --keep main` and merge the rest again), land the reader, and merge the row after it. Never land such a batch from `_merge`: the land refuses there, and its build is the branch's, which is how #4343 landed by hand.
- **A merge that changes how the harness keys or writes its readings.** Main's xtask holds each reading in `_merge`'s store to the key it computes itself, and refuses one of a `v` it does not know while it reads past a field it does not know (harness-design.md §4.2, #4404). A branch that changes a rule of `xtask/src/key.rs` (the closure, `BUILT_UNDER`, `READ_BY_TESTS`, `READ_BY_BUILDS`) has its lanes key their readings its own way, and the land lists them as stale; one that gives the reading a new `v` in `xtask/src/reading.rs` writes some the land lists as missing. A field added under the same `v` is not this case: main's reader reads past it, and `Store::land` keeps it in the index entry. Running the lanes again in `_merge` clears nothing, since the merge's xtask keys and writes them the same way again. The judge is not taught the merge's keying: one that read a reading as fresh under the rules it was written with would pass a branch whose key is a constant, the branch deciding its own land (#4372, #4378). So the land refuses, and where the batch changes a file under `xtask/` and a reading is stale or missing it names the case and prints the commands that take them, one a line, each the judge's own binary over `_merge`: `<main>/target/judge/<tip>/xtask --root <_merge> test --crate xtask`. Run them in `_merge` and land again; the merge then passes under the keying main holds. Land such a branch in a batch of its own, so the readings to take are the harness's `clippy` and `test` and not those of every crate the batch touches. After the fast-forward main's xtask is the merge's own, and what it finds depends on what changed. After a change to the keying, the readings the judge's binary took are stale under it, and the ones the merge lanes took in `_merge`, which the land put in main's store, are the ones it finds. After a new `v` alone the key is the same, so the readings the judge's binary took read fresh, in the `v` main wrote before, and the merge lanes' own lines are the ones lost: main's reader before the land refuses their `v` and keeps them in `log/unread.jsonl`. Where the push's `done` still names a reading, take it in main's checkout before the push.
- **A lock or a generated file main's xtask renders otherwise.** The judge takes `budget`, `api-check` and `unsafe-audit` itself over `_merge`'s tree: `api-check` regenerates each lock and diffs it against the one committed, and `budget` holds a generated file to what main's xtask generates. A branch that changes the rendering and commits the files rendered its way fails there, and no reading taken again clears it, since the file is the tree's. Where the batch changes a file under `xtask/` and one of the three fails, the land names the instrument and both things it can be, since it does not run the merge's xtask to tell them apart. Run the instrument in `_merge` first, `cargo xtask api-check`: where the merge's own xtask fails the tree as well, the tree is the batch's to mend, as when two branches each under a ceiling are over it together, which no hook saw where git committed the merge itself. Where the merge's own passes, the land holds the tree to what main's xtask holds it to, and the change is meant to land in two steps: first the xtask that changes the instrument, landed over a tree main's xtask passes, which its own must then pass as well, so the new xtask has to take the tree either way; then, once main's tip carries that xtask, the files rendered again, in a batch of their own. The same holds for any change to what one of the three holds a tree to, a line `budget` stops counting among them. Nobody has walked the two steps (#4405): where the first has no commit both builds pass, stop and say so there.
- **`Cargo.lock` moved.** The land runs `cargo deny check advisories sources` under main's `deny.toml`, never the batch's, with the cargo-deny release `DENY` names in `xtask/src/queue/judge.rs` (`cargo install --locked cargo-deny@<that release>`); a missing or older cargo-deny refuses rather than passes. A finding is the batch's to fix by updating the crate the advisory names, or a person's `ignore` entry with its reason; never a `deny.toml` the batch carries, which the land does not read.
- **A harness file changed in what binds**, a ceiling raised or a row dropped, is printed as a skip naming each path and does not refuse: a person's commit does that, and nothing yet tells it from an agent's (#4371). Read the lines before the push.
