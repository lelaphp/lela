# The harness for the third engine: design

This is the design of record for the harness. It is one living document: every section is at its current value, and the ledger in §1 records each revision with what changed, why, and the check that would show it wrong. Git holds the dated versions. `research/harness-research.r1.md` and `research/harness-research.r2.md` are the two earlier revisions, kept unedited as records; they are not read for anything this file marks current, and the "highest `N` wins" naming rule no longer applies to this note. Design of record for the engine: `third-engine-design.md`, one living document with a ledger on top, with `jit-design.md` for the compiled tier in the same shape; the `rN` files are records and are not read for anything current. Vocabulary: `CONTEXT.md`. Decisions: `docs/adr/0001` to `0006`. Architecture terms (module, interface, seam, adapter, depth, leverage, locality) are the `codebase-design` vocabulary.

**Question.** What should a harness, in Böckeler's sense, look like for the development and maintenance of the third engine, and how much of it does the design already prescribe? And, from revision 3 on: what shape does the harness itself have to be so that it does not drift the way the design revisions have already begun to?

**Sources.** The full citation lists are in `research/harness-research.r1.md` ("Sources") and `research/harness-research.r2.md` ("Sources"); this file cites them by the same short names (**HE**, **CE**, **Sensors**, **OpenAI**, **Stripe**, **Anthropic**, **Approved**, **CM** for `computed`, **FH-dts**, **FH-issue**, **Hooks-ref**, **Plugins-ref**). ## 0. The one-paragraph design

**One manifest, one reading, one comparison, one judge, one status.** The rules of the harness live in one tracked data file, `seams.toml`, and every rule sensor is derived from it. Every instrument ends by writing one reading of one shape to `target/harness/`, and everything an agent or a person reads about the state of the engine is a rendering of those readings by `xtask status`. Every comparison against the oracle crosses one seam in the oracle module, which owns the one table of accepted differences. The edit-time gate is one instrument, `xtask permit`, and both kinds of Claude Code hook are thin adapters over it; the definition of done is one instrument, `xtask done`, called by the Stop hook, by pre-push and by CI. The harness note is one living document, and it asks the design of record to become one too.

A snippet that ends its binary, on a signal or an abort, is that witness's failure alone, and the next is served by a binary started again. `compile-identity` loses its linked rung and dumps through the engine's binary, which honours php's dump flags. §4.5's condition 1, §7's witness rows and §8 say so. `php-linked` carries `pcntl`, as the CLI does, so a snippet that forks forks it and never the harness; the mark `process` still sends such a fence to `php-witness`. Nothing is reversed, so there is no ADR. Check: `cargo tree -p xtask -e normal` names no crate under `crates/`, `ext/` or `sapi/`, and a fence that sends `SIGABRT` to its server fails alone while the fence after it passes (`xtask/tests/witness.rs`).

**85. Revision 85 (2026-10-07).** The witness trace is a runtime switch, and the witness lane's binaries are the hosts' own. Settled by Mitchell in the architecture review of 2026-10-06 (Q17, its own ticket) and landed by #2168. `witness-trace` was a cargo feature of `php_engine`, carried up through `php_ext`, `php_bundle`, `php_sapi` and each host, so `php-witness`, `php-cgi-witness`, `php-fpm-witness` and `phpdbg-witness` were second builds of the engine beside `php`, `php-cgi`, `php-fpm` and `phpdbg`, and a witness run after a phpt run compiled the engine again. The feature is gone: the request holds its trace as an `Option` that is `None` unless its engine was built with `trace_natives_to` or its test served it traced, and the entry a `php_macros` expansion builds tests that field on its way in, one branch per native entered. `php_sapi::prepare` reads `PHP_WITNESS_TRACE` in every host, so the witness lane serves a `process` fence through `php` and a `request` fence through `php-cgi`, `php-fpm` or `phpdbg`, built as every other lane builds them; `oracle::hosts` names one binary per host. The branch's cost is a bench measurement on #2168 for a person to read. §4.5's condition 2 and §8 say so, and §8's sentence that the linked engine carries no `pcntl`, which revision 84 made untrue, now says what keeps the harness unforked. Nothing is reversed, so there is no ADR. Check: no `Cargo.toml` in the workspace names `witness-trace`, `PHP_WITNESS_TRACE=<file> php -r 'json_encode(1);'` appends `php_ext_json`'s `json_encode` to the file, and the witness readings of every crate are what they were with the feature.

**86. Revision 86 (2026-10-07).** §4.5 condition 2 says what a kernel is and that a crate the attributes anchor counts its kernels beside its natives, settled by Mitchell on #1711 (2026-10-03) with the amendment, in the ruling's words: "A kernel is a function of a crate's `ops` module, as the manifest's witness.coverage scope names it (design §8, `php_engine::ops`), `pub` or `pub(crate)` at indentation zero, covered by a fence in its own doc block; a crate the attributes anchor is counted by its kernels beside its natives." Condition 2 said what a native is and that a crate declaring no attribute keeps the subject count it had, and said nothing of a crate with both, `php_engine`, whose natives the attributes anchor and whose kernels the `ops` module holds; the witness instrument counts both, and the condition now says so. Nothing is reversed, so there is no ADR. Check: `cargo xtask witness -p php_engine` names a kernel without a fence of its own as missing, beside a native without one.

## 2. Vocabulary

From HE: a **harness** is everything in an agent except the model, narrowed here to the part a team adds around a product it did not build; a **guide** is a feedforward control that steers before the agent acts; a **sensor** is a feedback control that observes after; **computational** controls are deterministic and fast, **inferential** ones are model-run and slower; **keep quality left** distributes checks by cost, speed and criticality; the **steering loop** is the human iterating on the harness whenever an issue repeats. The full reading of the article, its principles and the claims it attributes to others is `research/harness-research.r1.md` Part A and is not repeated.

From this design: an **instrument** is one `xtask` subcommand that measures or judges something and writes a reading; the **seam manifest** is `seams.toml`; a **reading** is the one-shaped result an instrument writes; a **divergence** is one accepted difference from the oracle, a row in the registry the oracle module owns; a **rendering** is what `xtask status` produces from readings and the manifest. Cadences: **at the tool call** (milliseconds, `permit`), **on save** (seconds), **pre-commit** (under a minute), **per commit** (CI, the 4-minute phpt budget sets the scale), **nightly**, **per revision**.

## 4. The harness's own modules

Five modules, each deep: a small interface, most of the harness's behaviour behind it. All live in `xtask` (budget 14k, r3 §4.1) except the manifest and the registry, which are data at the workspace root and under `docs/`.

### 4.1 The seam manifest: `seams.toml`

**Interface.** One tracked file. Readers: `api-check`, `unsafe-audit`, `budget`, `permit`, `status`, the generator of `ext/clippy.toml`, and the test that runs one negative-control fixture per rule. Writers: people, in the same commit as the design change that alters a rule; the commit that lands a revision of the design of record is the commit that changes the manifest.

**What it declares, once.** Every rule the design of record states as a sentence today. The list is the acceptance test for the format: a rule below that the format cannot carry is a design error in this section.

```toml
# An excerpt of seams.toml; the file is the statement. One key per line: TOML
# has no statement separator, so `name = "x"; budget = 1` does not parse.
[oracle]
pin = "oracle.toml"                        # the only statement of version, digest, recipe

[budget]                                   # total, new, docs, harness, lock_packages,
                                           # clean_build_release_s, api_items, api_private_items, bindings:

[[crate]]

lock = ["api.lock", "sapi.lock", "tier.lock"]
lock_from = { "api.lock" = "php_ext" }
[[crate]]
name = "php_jit"
feature = "jit"
# ... one row per crate of design §4.1, ext/* rows with a ceiling each

[[seam]]

consumers = ["php_jit"]

```

Each `[[rule]]` has an `id`, a scope or a tool, one predicate, an optional `adr`, an optional `exempt` (paths the rule does not judge, in the scope's grammar; `permit` reads it for every predicate it judges, #23), an optional `exempt_label` (the tracker's labels under which the rule does not judge a call that names an issue, which only a rule `permit` judges at the call may carry, #341, ledger 53), and the `text` a failure prints. A tool is `Edit`, `Write` or `Bash`, the calls `permit` judges, or `Stop`, the hook event, for a rule `done --hook` reads over the reply and `permit` never judges (#32). The predicates are ten: `deny_types`, `allow`, `deny_pattern` (with an optional `unless`), `deny_argv` (with `with`), `on`, `deny`, `deny_lints`, `check` (a named `xtask` lint), `avoid_from` (a glossary file, or `{ file, section }` for one section of it alone, #63), and `generated` (a file and the rule it is rendered from). The one qualifier that is not a predicate of its own is `unless`: it names the instrument whose work the pattern describes, so that a hit that instrument left behind is that instrument's own and not the call's, judged by the instrument's reading and never by the shape of the call (§4.4). Each `[[seam]]` names its lock, and a lock with `sections` is diffed per section; each `[[crate]]` names its ceiling and nothing about `unsafe`; the `unsafe` homes are one rule and appear nowhere else in the file. That is the whole grammar, and `xtask` refuses a manifest with an unknown key.

Two tables beside the rules. `[telemetry]` carries the sensor telemetry's one number, `silent_days` (§7); it is optional, and while it is absent `status` renders no silent column and says which key is unset, since a default in code would be a copy. Each `[[week]]` is one exit bar of the thirty days (design §11): `days` as the table writes them, `text` in the design's words, and `reads`, the readings the bar is measured by, each the latest of an `instrument` over a `scope`, held on status pass or, with `number`, within `min` and `max`. A read names an instrument `xtask` has, so a row cannot arrive before the instrument whose reading it reads: the instrument ships its row, in the commit that fixes the number's name, and until then `status --section week` says "no reading" for the bar.

**What is derived.**

- `api-check` reads `[[seam]]` and `[[edge]]`: it regenerates each lock from the compiled crate's public items (`lock_from` says which crate for `api.lock`, r4 §4.5), the harness's own included (the `harness` seam, `xtask/xtask.lock`, whose consumers are none: nothing in the workspace imports `xtask`), fails on a diff, tags the seam's reading with the `<lock>-line` rule the manifest carries for it (`api.lock-line`, `xtask.lock-line`), fails a manifest edge not in `[[edge]]`, fails a `use` path crossing a seam, checks the bundle order is topological, prints each extension's `pub` beyond `extension()`, holds `api.lock` to `[budget] api_items` over every line but `__private`'s and to `[budget] api_private_items` over those (design revision 34: the helpers only a macro expansion names, listed and diffed like any line, capped apart so their growth is also a person's decision), and treats `allowlist = true` as "the consumer may import only what the lock names" (r7 §4.2).
- `unsafe-audit` reads `unsafe.homes`. `budget` reads `[budget]` and every `[[crate]]`.
- `ext/clippy.toml` is generated from `ext.no-locks`, `reason` strings included, and committed; a stale copy is a `budget` failure (the same rule as generated code, r1 §3 principle 7, applied to a config file). Clippy finds it by nearest-file search, so it covers every `ext/<name>` and nothing under `crates/` (revision 1 D.2).
- `permit` reads every `[[rule]]` with a `tool` or a `scope` (§4.4).
- `status --section rules` renders the rule list with its ADR numbers; that rendering is the map's item 7 (§5).
- One fixture per `[[rule]]` under `xtask/fixtures/rules/<id>/` that must fail, run by `cargo test -p xtask`; a rule without a fixture fails the test. This is Mahout's "a new instrument ships with its negative control" (r1 §2.1) as a structural fact.

**The deletion test.** Delete the manifest and every number and edge reappears in six places: `api-check`'s source, `unsafe-audit`'s source, `budget`'s source, `ext/clippy.toml`, the hook's rules, and the map. That is what the inventory found had already happened in the design revisions.

**What is not in it.** The oracle pin (`oracle.toml`, a human decision with its own nightly sensor, §10 rule 5). Divergences (`docs/divergence.toml`, §4.3). Anything decided in prose: the deletion-test arguments, the ledger, the principles.

### 4.2 The reading and its store

**Interface.** Every instrument ends by writing one reading; every rendering reads them; nothing else touches the store. One shape:

```toml
instrument = "witness"                     # api-check | permit | done | track-work | ticket | usage | budget | clippy | test | phpt | port-map | compile-identity | crosscheck | unsafe-audit | steer | divergence-reason | witness | vocab, the subcommands that write one, in cli order; bench | fuzz | mutants are named here and not built yet
scope = "ext/pcre"                         # a crate, a corpus subset, a gate id, or "workspace"
rule = "witness.coverage"                  # a manifest rule id when one applies
status = "fail"                            # pass | fail | skip
numbers = { run = 212, failed = 3, missing = 1 }
message = "ext/pcre: 3 witnesses differ from the oracle; preg_replace_callback lacks a witness"
adr = ""                                   # from the manifest when the rule names one
tree = "9f3c…"                             # git tree hash of the scope's sources at the time
commit = "0b62ae0"
at = 2026-09-07T01:05:49Z
session = ""                               # the hook's session_id on a permit reading; empty elsewhere
```

**Store.** Three things under `target/harness/` (revision 83). `<instrument>/<scope>.toml` is the scope's last reading, overwritten on each run. The index, `<instrument>/<scope>/<key>.toml`, is the latest reading of the scope over each key it was taken over, written whole by a rename so two writers need no lock, the newest 32 keys of a scope kept, and a reading taken under an oracle pin kept per pin, `<key>-<pin>.toml`: "the latest reading over a key", which `done` and every `--staged` instrument ask, is one file read. The log, `log/<instrument>.jsonl`, is append-only history, one line per reading and one file per instrument, read by the renderings of history (the permits section, usage, the dashboard) and by no question about a key, save `permit`'s look for evidence of a key the index has let go. A store written before revision 83 keeps one `log.jsonl`; the first record or read that finds it splits it into the log and the index and keeps it as `log.migrated.jsonl`. CI uploads the log as the run's artefact and nothing else. The `tree` field is what makes a reading fresh or stale without a turn counter: a reading is fresh for a scope when the scope's tree hash still matches.

**Readers.** `status` (§4.6), `done` (§4.5), the steering ledger (§10 rule 6), the CI summary that answers HE's "which sensor never fails" (§7). `permit` writes a reading per denial, which is the steering-loop capture of revision 2 without `$.store` or a second file. The dashboard reads readings through `xtask status --format jsonl --every --log`, never a log line's numbers itself, and names the xtask commit that rendered them. Which reading stands, and what a series sums, stay its own.

`session` is what makes "this session" of §4.6 a rendering rather than a guess: `permit` copies the hook's `session_id` onto every reading it writes, and `status` counts denials per session from the log.

**A bench reading's two halves.** `bench` is the instrument whose reading is not the whole answer, so its halves are named here and not inferred again at each bar. The agent's half is the run, and it is an ordinary instrument: `bench` measures the scope under the protocol this engine inherits — paired reps, the A/A control, status labels, load average recorded (`docs/perf/measurement-protocol.md`; third-engine-design.md §9) — and ends as every instrument ends, in one reading, scoped by the gate id or the bar's name, the measurement in `numbers` and `status` pass or fail against the bar. Its exit is 0 whatever the reading says, which is what `permit --bench` already turns on: a bench number is a claim a person reads with the A/A control (§4.4; revision 16, #61), so the agent states the measurement and never the conclusion (`AGENTS.md`). The person's half is the sign-off: reading the number beside its control and saying what it means — the perf claim itself, the revisit a missed G1 asks of `jit-design.md` §3, the cut order a missed weekly bar applies (§11). An acceptance criterion that wants both is therefore two boxes and not one: "a fresh passing `bench` reading at G1" is an agent's and is measured under the protocol, "the number signed off" is a person's, and a single box phrased as both can be ticked by neither.

**The deletion test.** Delete the store and nine channels reappear: `jq .summary phpt-last.json`, `jq` over the mutants outcomes, `wc -l` over the locks, `grep -c` over the divergence table, the `context` note, `harness-turn.json`, the `$.store` counters, `harness-steering.jsonl`, and a per-gate CI line. Revision 2 had all nine.

### 4.3 The oracle module owns the comparison and the divergence registry

**Interface.** One handle and four functions on it, plus the comparison pair. `Pin::oracle()` returns the oracle for one run: it asserts the pinned binary's digest once, before the first program, and refuses the whole run on a mismatch, so a lane that runs a thousand snippets hashes the binary once (revision 16). On it, `run` is revision 1's: run this program, SKIPIF or `-r` snippet under the harness regime and return normalised output (r3 §8); `run_under(invocation)` is `run` with the binary named rather than assumed, so a lane that measures the engine runs it under the one recipe and the two are comparable. An `Invocation` names the run, the binary and the program, and carries seven things over the recipe: five that a `.phpt` section adds, the ini after the recipe's, the arguments after the program, environment entries over the recipe's, what the program reads on stdin, and whether the second stream is the first; and two that no section gives, the `[regime.<name>]` of the pin whose ini stands between the recipe's and the test's, and the flags before the program, where php takes a mode of its own rather than a setting. `-l`, which compiles a program and does not run it, is the compile-identity lane's (#101), so that a corpus written to be run is compiled and never run to measure the compiler. The flag is on the invocation and not in the pin's `[regime.dump]` (#111): a regime is ini, `-d` after `-n`, and `-l` is not ini; the pin is a person's file with its own review (§11), so a lane that wants a mode of php would wait on a person for each; and `run_under` puts the same flags before the program for the binary under test as for the oracle, which is what leaves the compiler as the only difference between two dumps. Whether php prints its op arrays is the regime, and whether the program then runs is the flag. `oracle::normalise(rules, bytes)` is the recipe's CRLF and trim rule alone, which a stream and a `.phpt` expectation both go through, the stream then also losing its scratch prefix. The module also owns what every lane needs of the pin and nothing else does: the runner, which says whether a lane ran the engine, a control or nothing because the binary is absent; `Source::tree()`, the one answer to where the pinned php-src tree is: the directory `TEST_PHP_SRCDIR` names when it is set, upstream's own variable, and the pin's `[source].path` otherwise, which is the tree on the machine the pin was written on (#36); a test that would skip for a fact of the pin this machine has not, the tree or the binary, fails instead where the machine promised it through `XTASK_PROMISED`, naming what it looked for (#38), so a broken provisioning is a red test and never a quiet skip; and the expectation grammar (`--EXPECT--`, `--EXPECTF--`, `--EXPECTREGEX--`) a `.phpt` and a witness fence share. `oracle::compare(id, expected, actual) -> Verdict`, where `id` is a divergence key and `Verdict` is `Same`, `Diverged(Divergence)` when the registry has an accepted row for the id, or `Differs(diff)`. Every instrument that holds the engine to the oracle calls `compare` and never diffs on its own: witnesses (id `witness:<hash>`), phpt verdicts and the nightly runner control (id `phpt:<path>`, kinds `phpt` and `runner`), compile identity (id `compile:<path>`), the crosscheck lane (id `crosscheck:<name>`, kind `crosscheck`, one row per extension whose rendering a person has accepted apart from the oracle's), the trace dump diff (id `trace:<site>`), and the differential fuzzer, whose minimised failure is proposed as a row with status `open`.

**The tally.** The phpt and witness lanes, and the compile-identity lane when it comes, share one tally (`tally::Tally<J>`): it owns the runner ladder (a control is a skip and not a reading of the engine, an absent binary is a skip, the engine is pass or fail), the rule that nothing run is not a green reading, the print loop over every non-pass item and the reading it writes; a lane contributes its judgement variants and how to judge one item, and nothing else (revision 16). A `lane` is a scheduled run of a corpus (§7), never the tally.

**The registry.** `docs/divergence.toml`, one row shape:

```toml
[[divergence]]
id = "trace:nested-entry-return"
kind = "trace"                             # witness | phpt | runner | compile | crosscheck | trace
reason = "A trace rooted at the entry frame of a nested execute stops with Return one opline earlier than php's (jit-design.r3 §4.2)."
status = "accepted"                        # open | accepted | fixed
since = "2026-09-06"
```

The two rows the JIT note carries in prose and the runner disagreements revision 4 §12 allows in the first weeks are rows here, so the day-30 target (< 20 rows, r1 §8.5) counts every kind, and the "target zero" of the runner control is the count of kind `runner`. A Markdown rendering for people is a computed region in `docs/divergence.md` whose command is `xtask status --section divergence`; the region is the view, the TOML is the truth (CM-spec:3).

`oracle::verdict(registry, id, met, expected, actual)` is `compare` with the caller's match standing where byte equality stands, for an expectation that is a pattern rather than bytes (`--EXPECTF--`, `--EXPECTREGEX--`); `compare` is `verdict` with `expected == actual`, so one place decides what the registry means and the count of comparisons that consult it is still one.

**What the recipe's environment is.** The pin's `[recipe.env]` is the witness regime's: `TEST_PHP_EXECUTABLE` there names the pinned oracle, which is what a witness runs. A phpt lane runs a different binary, and the corpus spawns the binary under test by that name and by `TEST_PHP_EXECUTABLE_ESCAPED`, so the runner sets both over the recipe's and under the test's own `--ENV--`. The pin does not move for this: its value is right for the regime it states.

**What a crate row's oracle variant is.** Beside `[oracle]`, the pin carries `[variant.<name>]`: the pinned tag built with the main oracle's configure line plus the variant's `flags` and nothing else, so it differs from the oracle only where intended, with one table per platform its binary is pinned for (`darwin-arm64`, `linux-x86_64`, `linux-aarch64`; #1782, #1890). Every platform's table carries `path`, the install prefix #1889 builds to (`/opt/dax-php/oracle/<variant>/bin/php`), and the binary's `md5`; a relative `path` is the pin's directory's. A Linux table also carries `image`, the base image's manifest digest, which #1889 pins and rebuilds from, and the lane checks the binary by its md5; the macOS table, built on the maintainer's machine, names no image. A `[[crate]]` row's `oracle = "<name>"` runs that crate's `crosscheck`, `witness` and `phpt` under the variant's build for the platform the lane runs on, and every crate without the key under the main oracle. A variant is not a second recipe: `Pin::variant` is the pin with the variant's binary standing for `[oracle]`'s, so the recipe and its regimes are the main oracle's, an entry of the recipe's environment that names the main oracle's binary naming the variant's instead, and the binary's md5 is asserted once per run as the main oracle's is. An unknown variant fails that crate's readings, not the manifest: a row naming a variant the pin does not carry fails the crate in the three lanes, naming it, where refusing `Manifest::load` would stop `permit`, `done` and every lane over one row (revision 80, #1948).

A row whose one reason holds for many ids of its kind names them in `covers`, and `compare` reads an id in `covers` as it reads the row's own; the row counts once against the day-30 target, which counts reasons, not tests (revision 62, #1220). The fixture that fails without it is a `phpt:` id listed only in `covers`, read as `Differs`.

**Who writes a row.** A person, with a reason (§11). The fuzzer and `compare` may add a row with status `open` and an empty reason; `done` fails while an `open` row touches the scope.

**The deletion test.** Delete `compare` and four instruments each decide alone whether a difference is accepted and against which list; three lists existed.

### 4.4 `xtask permit`: the judge at the tool call

**Interface.** Input: one intended tool call, as the JSON the shipped hook receives on stdin (`tool_name`, `tool_input` with `file_path`, `old_string`, `new_string`, `content` or `command`). Output: the hook's JSON, either `{"hookSpecificOutput":{"permissionDecision":"deny","permissionDecisionReason":"<text> (ADR-0005)"}}` or allow with `additionalContext` carrying the notes; exit 0 whatever it decides, since the decision is in the JSON (Hooks-ref, PreToolUse decision control). The one non-zero exit is the refusal to decide at all: a build whose compiled digest of what it judges by is not the tree's, or one that cannot read the manifest (revision 13). Every denial, every note and every refusal is a reading with `instrument = "permit"` and the rule id.

**Implementation.** The `[[rule]]` rows of the manifest with a `tool` or a `scope`, evaluated in order: the region-body rule of revision 2 (an `Edit` whose `old_string` lies in a computed region body, CM ADR 0005), `witness.exit-authored`, `unsafe.homes`, `ext.no-locks`, `api.lock-line` as a note, `git.no-verify`, `lanes.nightly`, `computed.force`, `harness.self`. Argument parsing for `Bash` is conservative, splitting on unquoted whitespace and `;`, `&&`, `|`; pre-commit remains the sensor of record for what a shell can hide. Path to crate is one function over the manifest's `[[crate]]` rows.

**What an `unless` permits.** A `deny_pattern` row that names an instrument (§4.1) refuses an authored line and not the line itself, so the judge needs evidence of whose hand wrote it, and the evidence is the instrument's reading and the tree it is stamped with (§4.2, §13 D.18). A hit is that instrument's own, and permitted, when every match already stands in the file as the instrument last saw it: each match in what the call would write is in the file on disk, the file lies in a crate the manifest names, and that crate has a reading of the named instrument whose stamp is the crate's tree hash now. Where no such reading stands, a match is the instrument's own when the block around it, its line and the lines on either side up to a blank one, stands in the file as it was at one of the last commits to change the file whose crate a reading of the instrument was taken over, the commit's tree hash read from its objects, and the reading found in this workspace's store or in the store of another worktree of the clone (#1448): a merge makes a state of the crate no branch measured, and the line a branch's `--accept` captured is still the branch's capture; a block typed by hand stands in no commit an instrument measured. `witness --accept` writes the fence line and constructs its reading after, so the line it captured is inside the tree the reading is over. A hit neither kind of evidence covers is denied whatever the store holds. That is where an authored line is refused — at the call, before what it would write is in any tree — and equally where a line a hand left in the tree is refused, by `permit --diff`, the call pre-commit makes over the staged diff (§7), the crate carrying no reading of the instrument or one stamped with an older tree. Evidence the judge cannot read is no evidence: a file it cannot read, a path no `[[crate]]` row covers, a store or a git that answers with an error each leave the hit denied, where the row stood before the qualifier. The reading's own status is condition 1's to hold (§4.5) and is not read here: a failing `witness` is the instrument's to print, in its own words, and saying it again in the row's would name the wrong problem.

**Adapters, two.** The shipped command hook, always on: `PreToolUse` with matcher `Edit|Write|Bash`, command `xtask permit` reading stdin, in `harness-plugins/hooks/hooks.json`, a person's file under `harness.self`. The function hook, `harness-plugins/hooks/harness.ts`, on unless `functionHook` in the plugin's `userConfig` is set false: a `tool.call` handler on `Edit`, `Write` and `Bash` that writes the event in the command hook's stdin shape (D.16) to `$.process.run(["xtask", "permit", "--above-the-command-hook"], { stdin })`, returns `{ deny }` or `{ ...result, context }`, and calls `$.ui.invalidate("prompt.context")` after a `Bash` call that ran an instrument. It judges the call before the command hook does, and the flag says so: a denial ends the call there and is recorded there; an allow goes on to the command hook, which judges the same call and records the notes, so a note is one reading and not two. It adds nothing the command hook does not do except the invalidation and in-process latency; it fails open, and the command hook beneath it fails open, when no candidate judges at all, on `Bash` alone, a narrower hole than the module's, which is why the module may exist (revision 2 C.8 item 8; revisions 11 and 13). Each walks its candidates, every built `xtask` that stands and then `cargo run`, and takes the first that exits 0: `permit`'s exit is 0 whatever it decides, so a non-zero one is a build that never judged — one handed a flag it does not know, one that cannot read the manifest, or one whose digest of what it judges by, `seams.toml` and the `.rs` files under `xtask/src` written into the binary by `build.rs` and compared with the tree by `built` (revision 16: a swap file or a `.DS_Store` there is not a source and does not move the digest), is not the tree's — and neither adapter passes a call on that build's silence. The built two are walked in orders that are not equal, the command hook release first and the module debug first, so one stale build does not silence both layers at once, as it did on 2026-09-08. A built candidate's stderr is dropped and the cargo candidate's kept: a refusal from a binary the walk passes over is not a message for the model, and cargo closes the list, so its stderr is the one a person needs when every candidate refused (revision 16). `cargo run` closes both lists, and its build re-runs `build.rs`, so the candidate that rebuilds carries the digest of what it is about to read and a list cannot end in nothing but refusals for want of a rebuild. A call in another checkout of the repository whose manifest the build was not compiled against, a worktree laid before a `seams.toml` change, is not refused: the build hands it to that checkout's own `xtask`, the same walk over the worktree's built binaries and then `cargo run` there, rooted at the worktree, and returns its decision, so each tree is judged by the rules it carries; a hand-off no candidate judges is the call unjudged (revision 60). The command hook is two entries over that one walk: on `Edit` and `Write` a list no candidate judged ends in a deny, since a write no judge saw does not proceed, and on `Bash` the call is handed on, since an agent repairs a broken harness with `Bash` and denying all three deadlocks the repair (revision 13). A third caller is pre-commit, which runs `permit` over the staged diff as a whole.

**What the seam does not cover.** The seam is only as good as the set of tools that cross it: the matcher is `Edit`, `Write` and `Bash`, so a GitHub MCP server attached later would not be judged at all, and `xtask ticket` is the closer only for what reaches the hook. The tracker is `gh` and nothing else, no trait and no second adapter, until a second tracker exists to make a seam real (#28).

**Cost.** `cargo run -q -p xtask -- permit` after a warm build is a process start and a manifest parse, tens of milliseconds; an `xtask` binary installed by `cargo install --path xtask` is the same without cargo. The bar: p99 under 100 ms at the tool call on the developer machine, measured by `permit --bench`, a measurement and not a gate: its reading carries pass or fail against the bar and its exit is 0 whatever the reading says, since a bench number is a claim a person reads with the A/A control (AGENTS.md; revision 16, #61). If it is missed, the manifest's rules are compiled into the binary at build time and the parse goes away; the interface does not move.

**What leaves the harness.** `rules.ts` and its tests. The function hook is enabled (revision 10), so the adapter, its tracked `tsconfig.json` and the regenerated declaration file stay, and the test job holds them: it installs Claude Code at a pinned version, writes the declarations with `/plugin-types`, runs `tsc -p harness-plugins` and `claude plugin validate --strict` (revision 16, #53). The `types-version` region that would make the pin a sensed fact is postponed (#62).

**The deletion test.** Delete `permit` and the rules are evaluated twice, in Rust after the write and in TypeScript before it, on a surface whose events "may change between releases without notice" (FH-dts:1-6).

### 4.5 `xtask done`: the definition of done

**Interface.** `xtask done [--base <ref>] [--hook]` prints the conditions of done that are unmet for the changes since `--base` (default: the merge base with `main`, the checkout's branch where it has one and `origin`'s otherwise), exits 1 if any, 0 if none; with `--hook` it reads the Stop hook's stdin, exits 0 when `stop_hook_active` is true, and otherwise prints `{"decision":"block","reason":"<the list>"}` (Hooks-ref, Stop).

**The conditions**, from revision 1's map item 6, now checked rather than stated:

1. For every crate with a changed file, a fresh passing reading exists for `clippy`, `test`, `witness`, `api-check`, `budget` and `unsafe-audit`, for `phpt` on that crate's subset where the crate is one the binary under test carries, whose subsets the per-commit lane runs (revision 63), for `port-map` where the crate is the one `api.lock` lives with, `php_ext` today, and for `crosscheck` where the crate is an extension of the default set, the ones the lane renders per commit (§7, #269), in both of its columns: the `--re` reading under the crate's name and the `--ri` reading under `ext/<name>/ri`, one sensor rendering one extension twice and a touched extension held to both (#361, #273). `test` is the crate's own tests, `cargo test -p <crate>` as a reading (#191), and it is narrowed for nobody: every crate has tests, the harness included, and a crate whose tests do not run is not done. It is a reading rather than a line in the pre-commit script because every other thing this condition asks is stamped with the crate's tree, so it is fresh or it is stale and a session that changed a file after running the tests is caught; a bare `cargo test` in a hook answers only for the moment it ran. What it costs is the run itself, `cargo test -p xtask` above all, and the instrument carries the `--crate` and `--staged` narrowing the others have, so a session pays for the crate it touched and CI pays for the workspace. A crate the manifest marks `feature =` is outside that build, its corpus is the nightly lane's, and `done` does not ask it for a reading no lane run writes (#133, §7). `port-map` is asked of that one crate and of no other, because it writes exactly one reading and that is the scope it writes it at (`port_map::home_of_the_lock`, design §4.4); asked of every touched crate it would hold each of the others to a reading nothing ever writes, so the ask is narrowed in `done::instruments_of`, where `witness` and `phpt` are narrowed already, and is not a row of `done::FRESH` on its own (#148). That crate is the one to ask because the lock is in its tree: an unmatched row is the join's failing half, what the lock carries or does not carry is what makes a row one, and a change to `api.lock` therefore stales the reading and `done` says it a turn before the per-commit lane does. The join's other input is wider than its home and this condition does not reach it: an extension declaring its first native leaves rows resolved without touching `php_ext` (design §4.4, §11), and that number is the port's schedule and no condition of done, measured by the lane per commit like any other. Fresh means the reading's `tree` matches the crate's tree hash now. One reading is met without passing, and it is the only one: the `phpt` skip the missing engine binary causes, which says the engine has no binary to run the corpus through (#132). There is none until `crates/php` reaches `serve`, so while it is absent every crate that owns a subset is unmeetable, #100's twenty `ext/` crates among them. Three ways were open — build `crates/php` and `php_sapi` far enough for the corpus to run, serve a `.phpt` in process the way `witness` serves a snippet, or excuse the skip — and the third is taken, with its cost stated rather than hidden: a crate is done with its corpus unrun, which is the price of the alternative, every extension port after #100 unmeetable from its own scope. The skip is held to its cause and not to its numbers, having none worth holding, since nothing ran at all. `engine_absent` on the reading is how the lane says the binary is what stopped it and not that the subset was empty, which it alone can tell from a subset of a crate not yet created and from one whose every test skipped; `failed`, `diverged` and `borked` are zero beside it, so nothing the lane did read counted against the crate. `witness` had a rung of the same shape while the binary was why its reading was a skip, held to its numbers, something run and nothing failed or missing (#106), and has none now: the linked engine serves every snippet, `php-linked` in a process the lane starts since revision 84, so its reading is a pass or a fail on its own merits (#119). This one goes away by itself when the binary exists. A `.phpt` the compiler refuses with its own parse error, the `cannot read yet` refusal `php_compile` raises for a construct it does not read, is a skip of the compiler's and not a failure of the crate: the lane tallies it as `unread` on the reading, names the count, and the subset's status is over the tests the compiler read. The skip is held to its cause, a parse error the compiler itself raised before any test code ran, and to nothing else, so a test that parsed and then failed, on a native another extension does not declare included, still counts against the crate. A subset whose every test is unread reads `skip` with `unread` equal to its count, met the way `engine_absent` is, and this rung goes away by itself as the compiler reaches the corpus (#319). A third rung is the manifest's rather than a lane's. An extension whose port is not finished carries `porting = true` on its `[[crate]]` row, and while it does, its `crosscheck` and its `phpt` readings are the port's meter rather than a condition of done: the numbers are printed and the row is met whatever they say, the way the `engine_absent` skip is met (#383). Everything else a touched extension is held to stands unchanged — `clippy`, `test`, `witness`, `api-check`, `budget`, `unsafe-audit` and `vocab`, and the witness on every native it declares. The reason is the shape of those two sensors and of no others: both measure one extension against the whole of the oracle, every declaration `php -n --re <name>` renders and every `.phpt` under `ext/<name>`, so an extension whose port has forty natives of six hundred fails both from its first commit to its last, and held to their status they stop every commit that touches it however green its own work is. #325 landed `sleep()` and `array_unique()` with every reading of its own passing and could not close; #340 and #337 stood on the same line. Two other shapes were open and are refused. A regression floor, a pass count per crate that may not fall, is the honest sensor and the number moves with every port commit, so it is a manifest write per commit and `steer` refuses a changed value by construction: it puts a person in the loop of every port commit, which is the cost this rung exists to remove. Chartering the port as fog with the two rows standing leaves no sensor at all. What holds the key honest: the readings are still asked for and still have to be fresh, so a session that touches the crate runs both lanes, and `xtask status --section crosscheck` and `--section phpt` render every row with its numbers whatever the key says, so a port that goes backwards is visible in the console and in CI's log; and the key names one crate, so a crate without it is held to both readings the day it is created. This rung does not go away by itself, as the other two do: it is deleted, one extension at a time, and the day the key goes the extension is held to the oracle's bytes and its whole corpus forever after, which is the port's completion certificate.
2. Every kernel or native added in the diff has a witness (the `witness` reading's `missing` is zero for the crate). A native is a `fn` under `#[php_function]`, or a method with a body in a `#[php_class]` impl, at any indentation and visibility; a body-less member and an `implementation =` alias are not subjects (design §8, revision 34). A subject is covered when a fence of its own, or for a method a fence on its class's header or member impl, enters it while the linked engine runs that fence (revision 58). The entry a macro expansion builds records itself on the way in, in every build, and records nothing until the witness runner switches it on for a request or a host's binary finds `PHP_WITNESS_TRACE` set (revision 85). A spelling in a fence's text covers nothing: a fence covers what it ran. A crate that declares no attribute keeps the subject count it had. A kernel is a function of a crate's `ops` module, as the manifest's witness.coverage scope names it (design §8, `php_engine::ops`), `pub` or `pub(crate)` at indentation zero, covered by a fence in its own doc block; a crate the attributes anchor is counted by its kernels beside its natives.
3. If a `.lock` differs from its regenerated form, the lock file is in the diff (the `api-check` reading, plus `git diff --name-only`).
4. No `open` divergence touches a changed scope.
5. `permit` over the diff denies nothing.
6. `seams.toml` and `docs/divergence.toml` are unchanged in the diff, or the diff is by a person (the hook cannot tell, so the Stop hook reports it as a note, and pre-push, run by the person, passes).
7. The ticket the branch records (`branch.<name>.ticket`, the record `xtask worktree add --ticket` writes) has no unticked acceptance box, or was withdrawn, read from the `ticket` reading over its number and never from the tracker (#31, #221). A ticket has no tree of its own, so the reading is stamped over the workspace and is fresh while the workspace's tree hash still matches: every write after the read stales it, the ones an instrument makes included, so on a branch with a ticket `xtask ticket read` is the last act of a turn that wrote anything, one tracker call per such turn, outside the hook. `done` itself is computed from git and the store alone and reaches the tracker nowhere, the Stop hook included. What this does not catch, accepted: a body edited at the tracker while the work stands still is a green `done` until the next edit of the work. Condition 7 holds the branch's ticket to the `ticket` reading over it: met when the reading passes with every box ticked, or with `withdrawn` set, the instrument having settled the ticket either way; held while a box is unticked, while the ticket carries no box and is not withdrawn, or while the reading fails (#221). The one exception, standing from #31: a close the tracker refused with every box ticked is met, the boxes being the condition and not the close. A branch that records no ticket, and a detached `HEAD`, are not asked and nothing here says the word, the way `xtask` is not asked for a witness. In practice this is the Stop hook's and pre-push's condition: the record is the clone's own configuration, which a push does not carry, and a pull request's checkout is detached, so CI's `done` is not asked.

**Callers, three.** The Stop command hook, pre-push, and CI per commit. One instrument, one list; an agent and a person are told the same thing. A caller passes a base only where it knows one the branch cannot say: the Stop hook passes nothing and is measured since `main`, pre-push passes the remote's sha per ref, and CI passes the ref a pull request targets, its checkout being a detached merge commit on no branch, and nothing on a push.

**The reply, at the Stop alone.** With `--hook`, `done` also reads `last_assistant_message` for a session the store says closed a ticket (a `ticket` reading of a close carrying the hook's session), and holds the turn once when a sentence of it matches the `deny_pattern` of a `[[rule]]` with `tool = "Stop"`, the sentences named and a reading of `done` over the rule written. A sentence naming a ticket other than the one closed does not fire. This one is a heuristic beside the structural conditions on the close: a false positive costs one turn, since the second Stop passes and the recovery is to file the ticket and stop again; a false negative is the state before it (#32).

**The deletion test.** Delete `done` and the definition is seven sentences in the map plus a file protocol between `turn.step` and `stop-gate.sh` that checked one of them and only inside Claude Code.

### 4.6 `xtask status`: the one renderer

**Interface.** `xtask status --section <name> [--format md|json|jsonl] [--every [--log <file>|-]] [--uncut] [--week N] [--session] [--session-id <id>]`. Its sections are the ones `xtask status --help` lists, each a rendering of the readings and facts it names. `rules` is the manifest's rules, each with its ADR number, the predicate that judges it and its reading; the text its failure prints is in `--format json` and under `--uncut`, so the map carries the rules without it. `locks` is also the `api-check` readings' section (`--section api-check`). `--session` prints the map file and the local facts in one block for the function hook's `prompt.context`, takes the session's id from `--session-id` or the hook's stdin head, and appends this session's denials after the local facts, nothing when it has none; the local file's `permits` region stays without it, since `computed run` has no session to hand `status`.

It reads the manifest, the registry and the store, and what the repository and the pinned tree hold on this machine (the `git`, `oracle` and `parity` sections), only ever reading them: never the tracker or the network, never a build or a run. It computes nothing else; a section that needs a command of its own is a missing instrument, not a shell one-liner in a region.

With `--every`, a section that keeps one reading per scope renders every reading instead, in the log's order, and picks none; with `--log <file>`, or `-`, it renders a log it is handed, another store's or the published history, in place of the checkout's store. Under `--format jsonl` each row carries `v`, the version of its shape, which changes only when the shape does; a reader refuses a `v` it does not know.

A field a row may omit, whose absence a reader of the earlier shape already handles correctly, is added under the same `v`; a field removed, renamed or retyped, or a meaning changed, is a new `v`.

**Worktrees.** Every ticket is worked in a worktree on a branch cut from `main`, `t<n>`, laid by `xtask worktree add <branch> --ticket <n>`; `xtask track` answers what the two halves and `done` ask: the branch, the base, the main checkout whose `target/harness` is the one store, and the ticket the branch records. `add` cuts the branch from `main` (`origin`'s where the repository has only that), lays the worktree beside the checkout, at `<parent>/<checkout's name>-worktrees/<branch>`, which for main's checkout `~/Projects/dax-php` is `~/Projects/dax-php-worktrees/<branch>`, and never under `.claude/`, whose files are the harness's own (revision 56). Where one goes is `worktree::home`'s alone, and only `add` asks it: a worktree that exists is found through git's own record, `git worktree list` for `retire`, `track` and the console and its `.git` for `permit`, which judges a call in any checkout of the repository against that checkout's manifest, so a worktree laid under `.claude/worktrees/` before revision 56 is judged and retired as any other. `add` then makes three facts about it measured rather than guessed: it builds `xtask` there, so an `Edit` from the first tool call is judged by a built binary and not by a cold `cargo run` inside the hook's timeout (§12 item 8); it lays `.claude/harness.local.md` down through that build and renders it through `xtask regions`; and a grant covers every repository under the granted path (#74, §11), so the one that covers the worktrees is the grant over `<checkout's name>-worktrees`, made once per checkout: where `computed` answers untrusted, `add` prints that line as a person's and waits on none. The worktree's `target/` is its own, and `add` seeds it from the clone's `target/debug` with `cp -c`, a clone-on-write copy where the volume supports one: the registry dependencies are then blocks the two directories share and cargo rebuilds only the workspace's own crates, measured at 10 s of seeding against a cold dependency build, with `xtask` then built in 7.6 s. What it must not do is give two worktrees one `CARGO_TARGET_DIR`: cargo keys a workspace member's artifact by its path under the workspace root and judges the slot fresh by mtime, so two worktrees share one slot per crate and a checkout whose files predate another worktree's build runs that worktree's binary — measured on cargo 1.95.0, `cargo run` in one worktree executing the other's code with the other's `CARGO_MANIFEST_DIR` baked in (#251). The harness rests on the opposite: `built_root` resolves `--root` to the workspace its binary was compiled in, and `built::judges` and `permit` compare digests against that same root. Seeding is best-effort; where `cp -c` cannot, the worktree starts cold and nothing else changes (revision 40). What the clone already carries it reports rather than sets again: `core.hooksPath` is repository config, `.claude/settings.json` and `oracle.toml` are tracked, and the php-src tree the pin names is found through the oracle module (§4.3): `oracle.toml`'s `[source].path` is where the tree is on the maintainer's machine and stays so, and a machine that is not the maintainer's, a worktree on another box or the runner, sets `TEST_PHP_SRCDIR` to a checkout at the pin's tag, which `Source::tree()` reads first and holds to `[source].commit`. A branch the repository or `origin` has, and a directory that exists, are refusals that change nothing, as `new-ext` is. `xtask worktree retire <branch>` is the other half, and it is where the checkout keeps its evidence: a worktree's readings live in its own `target/harness/` and removing the worktree removes them, so the worktree's log is landed in the main checkout's store, the one `xtask track` names, each reading in its log and its index (revision 83), and only then is the worktree removed, which keeps a merged agent's denials in the `permits` section the console reads (§4.2). The scope's files beside the log stay with the worktree: each is a scope's latest run over a tree `main` does not have, and copying one in would hand `done` a reading that is fresh for nothing (#35). The branch is kept; deleting it is a person's line, printed. Both halves are held by `cargo test -p xtask --test worktree` against a scratch repository whose `xtask` is this one, built at its own HEAD.

**A track's plan.** What a track works next is the tracker's and no session's. `xtask track next` names it: of the open tickets labelled `ready-for-agent`, those no ticket blocks while it is open or while the branch that records it is not yet in `main`, that are the track's (carry its `track:` label, or, for `main`, no `track:` label at all), and that no branch of the repository records, the widest by the census, the number breaking a tie (#618); `xtask track work --track <name> --model <m>` lays a worktree down per ticket and runs the frontier until none is named. A closed ticket's branch is left for /specs to merge (#1749). `xtask track chains` prints the same open tickets whole, each under the one that blocks it, with its label, its branch and what it waits on on every line, so a session sees the frontier and what stands behind it in one call rather than a walk over `blockedBy`; it decides nothing and writes no reading (revision 26). What fills that frontier is the track's chart on the tracker, one issue labelled `frontier:chart` whose open tickets are its sub-issues. It is not the map: the map is `AGENTS.md`, which the head of this section names, and the two were one word until `CONTEXT.md` settled them apart (revision 22); one is where a session starts, the other where the track is going. The `/frontier` skill is the only thing that writes it: `chart <track> <days>` lays it down at one row of design §11's table, Destination from the row's exit bar, the work not yet sharp enough to ticket sketched as fog, and files the first batch; `work <track>` files the next batch when the frontier empties, indexing each close since the last batch into the route walked and graduating the fog those closes made sharp. The chart indexes and never restates, the detail staying in the ticket, so a session loads it cold in one read. A batch is three to five tickets, each one concern of the row sized to one session, and a ticket is of one of three kinds: a build, a fact outside the tree that a decision waits on (`frontier:research`), or a question the design of record does not make (`frontier:decision`). The kind is a label, and the label is the one thing `track work` changes between tickets, since it chooses the skill the session starts on: `/implement <n>`, `/research <n>`, `/grill-design <n>` (#81). With `--fill` an empty frontier starts a `/frontier` session; without it the run ends there. With `--fill`, a frontier emptied only by held tickets ends the run, naming each held ticket and the branch it waits on. Planning measures nothing and decides nothing: the row's exit bar is read from the instruments, the next row is charted by a person, and a question the design is silent on is a person's (§11).

**Per-directory guidance.** `ext/AGENTS.md` with the extension template rules (one dependency, `extension()`, state on the value, no locks, tests through `Capture`, witnesses in rustdoc, phpt from every `.phpt` under `php-src/ext/<name>`, as run-tests.php walks the directory, revision 67) and two regions, `extensions` (`tree src=. depth=1 dirs`; `ls -d */` fails on an empty `ext/`) and `bundle-order` (`xtask status --section bundle`). `xtask new-ext <name>` lays the topology down. **What else is computed.** `data/INDEX.md` gains a `files` region. Design documents get no regions and no numbers: they cite `seams.toml` and `oracle.toml` (§14).

**What CI's corpus covers now** (revision 17). The test job has the corpus: php-src checked out sparse and shallow at the pin's tag, by the patterns `xtask status --section corpus` renders from `phpt::ROOTS` (`Zend/tests`, `tests`, every `sapi/*/tests` and every `ext/<name>` whole, the directories the nightly lane walks and every `[[crate]]` row's subset stands under), cached by the pinned commit and a digest of those patterns, pointed at by `TEST_PHP_SRCDIR`, refused when its `HEAD` is not `[source].commit` (#37) and when it holds fewer `.phpt` files than `[source].phpt_files` counts (#1713). The job promises the tree and not the binary: the pinned php is a macOS keg the ubuntu runner cannot have, so the tests that spawn it skip there, stated, and the witness lane's readings are the maintainer's machine's (§13 D.20). What runs against that corpus per commit today is the runner control, `ext/pcre@control` under the pinned oracle where a machine has it, and the subset resolution of every corpus lane; the phpt rows above stand as the plan for the day the engine executes a script, and the row changes when a lane does.

**What the workspace's `test` row holds, and what it cannot** (revision 49, #389). The row runs and always has: CI's `xtask` job runs `cargo test -p xtask` and the per-commit job runs `cargo xtask test` over the workspace, on every commit pushed. What it cannot reach is a test that returns for want of the pinned binary. The runner promises the tree and not the binary, as the paragraph above says, so every test that spawns the oracle returns at its first line there and the readings those tests hold are the maintainer's machine's alone; an oracle the runner can have is a person's, and #424 is where that decision is filed. Until it lands, a test of the harness may not assert as an equality a number another crate's commits move: it goes red on one machine at that crate's commit, with no lane to say so, and is paid for by whichever session next touches `xtask`. What such a test asserts instead is read off the reading it has just taken — the counts, the status they imply and the message from the counts — and a **floor** stands beside it, a constant an advance never moves and a regression falls through, raised by hand beside a commit that wants it raised or not at all. The two that carried the pinning shape are `xtask/tests/compile_identity.rs`, whose `REACHED` is the files of the fixture corpus the linked compiler has come to, and `xtask/tests/crosscheck.rs`, whose `FLOOR` is the scopes whose rendering is the oracle's; each carries the negative control that shows its floor firing. This says nothing about `done`, which reads a crate's own readings and not the harness's tests, and nothing about a regression floor on a port, which §4.5 condition 1 refuses for a reason that stands: that one is a manifest value moving per commit, and these are a constant in the harness's own tree, moved by the session that touches it or never.

**Which subsets a lane runs has no home yet.** The per-commit row above names its four groups in this table and nowhere a command can read, so `xtask phpt` names no lane of its own: it runs the subset it is given, or every subset of the corpus under the whole-corpus flag, and a bare call says so rather than keeping a second copy of this row. The manifest is where the row belongs, as `[[week]]`'s reads are, and until it has one the lane is composed by whoever calls the instrument (revision 12).

**What the default build is, and where it is stated.** The per-commit row's default extensions are the design of record's: enable and disable live on `php_bundle` alone, one feature per non-default extension, and the default features match php-src's default `./configure` set as far as ported (design §4.10, and §8's `ext/<name>` row, per commit for the default extensions and nightly for the rest). At the pinned tag that set leaves four of the twenty out — `ext/mbstring`, `ext/pdo_mysql`, `ext/openssl` and `ext/curl`, each an `--enable` or `--with` whose `config.m4` gives no default — and those four are the ones `seams.toml` marks `feature =`. So the manifest's `feature` rows are the statement the lane filters on and `done` asks by (§4.5 condition 1), and they are the one the harness reads: widening the lane to every crate the bundle builds was the other way through #133's friction and is refused here, since it would run per commit what the design schedules nightly. `php_bundle`'s `default` names those sixteen and not the four (#159), so the two files name one default build and a reader is not choosing between them: the four are features a command line turns on and no build starts with, and the bundle's own comment says so. `new-ext` still lists every crate it lays down in `default`, and the pruning stays the person's act that comment reserves, done once per non-default extension as it is ported (design §4.10); so a crate laid down after this reads wider until that act, and what the harness reads is the manifest throughout. The witness lane does not stand on the rows (revision 43, #314): the linked engine the harness builds carries every extension feature, so a `feature =` crate's witnesses read pass or fail on their merits under the linked runner, and the rows filter the binary and the phpt lane alone. It resolves no binary either (revision 48, #401): every snippet is served by the linked engine whether or not `target/*/php` stands, since that binary is the default build and a fence held to whichever rung happened to run reads pass or fail by the tree's state and not by the code beside it. The one exception is a fence marked `process` (revision 61, #1062): pcntl's, posix's that change the process, and any other whose snippet forks, sends or takes a signal, or sets the process's ids, session or limits, is served by the `php` binary, which the lane builds itself, so the fence reads pass or fail by the code beside it and never by which binary stood in the tree. The linked engine is `php-linked` since revision 84: `sapi/cli` built with the bundle's `linked` set, every extension feature, `pcntl` among them since the CLI carries it, in a process of its own, so a snippet that forks forks it and never the harness.

**What the per-commit lane measures** (revision 63, #1261). The per-commit phpt lane measures every extension the binary under test carries, not the bundle's default set alone: the rows whose `feature` the `php` binary turns on (openssl, bcmath, calendar, pcntl, posix, sockets, bz2 at this revision; under ADR-0008 the features `sapi/cli` turns on), beside the rows with no `feature`. The binary the lane runs is that build, the oracle is built with those extensions, and parity is every test the oracle runs (third-engine-design.md §1, #1161); an extension the binary serves and the lane never measures is a gap the dashboard reads as nothing. A `feature` row the binary does not turn on stays out of the lane and in the nightly. The paragraph above still says which features are php's default `./configure` and so which `php_bundle` starts with; it no longer says what the lane runs.

**Which build a correctness lane runs** (revision 82, #1994). Every correctness lane (witness, the per-commit phpt lane, Zend/tests, `tests/*` and the nightly full run) runs the `release-da` profile: release with debug assertions and overflow checks, without thin LTO or a single codegen unit. The bench lane and the shipped binaries are plain release. The profile is `Cargo.toml`'s `[profile.release-da]`, and the harness names it once, in `xtask/src/oracle/profile.rs`: `phpt` looks for the engine's binary under that profile's directory first, then release's, then debug's, passing over one the tree has moved past as it passes over any (#475), and the cargo line a stale binary's skip names builds it; the witness lane serves its fences through `php-linked`, which it builds in the harness's own profile, and it builds a `process` fence's host in that same profile. CI's oracle job builds the harness, the hosts and the tree's test in it, and runs the nightly lane through that harness too.

**An extension whose port is partial.** The `phpt` and `crosscheck` rows above run per commit for every default extension whatever its port has reached, and both measure one extension against the whole of the oracle. An extension whose `[[crate]]` row carries `porting = true` is run by both lanes at the same cadence and rendered with its numbers by `xtask status`, and what the key changes is `done` alone, which reads those two readings as the port's meter and not as a condition while the key stands (§4.5 condition 1, #383). So the two manifest keys the lanes are read through say different things and neither is a copy of the other: `feature =` says which extensions a lane reaches, and `porting` says what the readings of one it reaches bind. The key is one crate's, added by a person and deleted by a person; a crate that carries neither is run per commit and held to what the run says.

**What the agent sees.** The tool result, as before; and beside it the rendering. `permit`'s note or denial arrives as the hook's `additionalContext` or `permissionDecisionReason`, with the ADR number from the manifest. The map's numbers are `status` renderings, refreshed by the session hook, by the function hook's invalidation when enabled, and by the next `computed run` on the local file otherwise. `done`'s list is the Stop hook's `reason`. A person sees the same renderings in the terminal and, per CI run, the uploaded `target/harness/`.

**Sensor telemetry.** The CI summary is `xtask status --section permits` and a query over the log: readings per instrument, failures per instrument, and the instruments with no failure in fourteen days, which are the candidates for "silent" (HE, open questions; Sensors, appendix). The negative-control fixtures of §4.1 are what separates silent from respected for the rule sensors; for the phpt runner it is the nightly control; for `permit` it is a fixture tool call per rule.

**Mutation testing and concurrency** stand as revision 1 had them: `cargo mutants --in-diff` per commit on `php_engine` kernels and `php_compile`, reported; full nightly on `php_heap`; `Cache` under Miri's data-race detection on a `std::thread` test, with loom priced as revision 1 D.4 says.

## 8. The behaviour harness

Unchanged in substance from revision 1. The behaviour specification is the oracle, the test bodies are php-src's, and a witness is an approved scenario (Approved) whose approval is the oracle's bytes, "captured and never authored" (r4 §8). What the harness protects is the choice of snippet: the `port-map` join says the minimum each native's witness must cover, mutation on the diff says whether it pins the branches touched, and human review of witness diffs is the inferential sensor. Revision 3 adds one thing: the registry. A witness that differs from the oracle is a `Differs` verdict until a person writes the row, and `done` will not pass while the row is `open`. Revision 48 adds what serves one: the engine linked into the harness, in this process, and never the engine's own binary (§7), so a witness is a claim about the kernel or native beside it and never about a build's enabled set. Revision 84 moves that engine out of the harness's process and keeps the rest: `php-linked`, `sapi/cli` built with the bundle's `linked` set, serves each snippet with a fresh engine as the harness once did, started by the lane and handed one snippet after another, so the harness links no engine and an edit under `crates/` or `ext/` rebuilds that binary and never the one every hook runs. A snippet that ends the binary is that witness's failure alone, and the next is served by a binary started again.

Revision 50 adds the one case where the oracle cannot be made to run the snippet at all. A branch whose state no PHP snippet can build — not one that is hard to write, but one the language cannot express here — is held by a unit test over the copied algorithm, and the box that asks for a witness is ticked by that test, under three conditions. The commit says in its own words why no snippet reaches the branch: which construct the compiler does not read, or which release php does not make. The test holds php's algorithm and not the engine's convenience: the text, the code and the order php's own source produces, cited by file and line at the pinned tag. And the fence is owed as soon as the branch is reachable, the ticket that makes it reachable named in the commit where one exists and filed where none does. `witness.coverage` is untouched: the kernel or native carries its fence wherever the oracle can run one, and this is the narrow case where it cannot. The one instance today is `zend_objects_destroy_object`'s `Attempt to destruct pending exception` (`Z/Zend/zend_objects.c:157`), held by `api::request::tests::a_destructor_served_on_the_pending_throwable_is_the_core_fatal`; what the third condition means where php's own algorithm is what keeps the branch out of reach, rather than this engine's compiler, is #458.

Revision 55 adds what a witness runs under. A witness is approved against the pin's `[recipe]`, and that does not change: the recipe is what a fence stands on when it names nothing, and its authority is that a person wrote it. What a fence may do beside that is name one `[regime.<name>]` of `oracle.toml`, whose ini stands after the recipe's for the oracle run and for the linked engine alike — the same block, in the same order, that `compile-identity` names as `dump` and the tier lanes name as `jit-tracing`, `jit-off` and `jit-inline`. The reason is that a behaviour whose entry the recipe pins away is otherwise outside what a witness can pin at all: the recipe passes `short_open_tag=0` and php registers that entry `PHP_INI_SYSTEM|PHP_INI_PERDIR` (`Z/main/main.c:820`), so no snippet asks the oracle what `<?` opens while it is on, and `short_open_tag` is only the first such entry to be found. A regime is a named, reviewed, reusable row of the pin, so the fence carries the name and the pin carries the values: a fence that would set an ini of its own is refused, since it would let a fence approve itself against a pin nobody wrote. A name the pin does not carry is read off the pin before anything runs, and the block is one the lane cannot run, named beside the regimes the pin has.

Revision 61 adds the one fence the linked engine does not serve. A fence whose `expect` line carries `process` says its snippet changes the process it runs in: it forks, sends or takes a signal, or sets the process's ids, session or limits. The harness runs its lane on threads, and in such a process a `fork()` copies one thread of many with whatever the others held, a signal lands on whichever thread the kernel picks, and a limit or an id set is the harness's own; design revision 35 builds pcntl for the single-threaded `php` binary alone for the same reason. So such a fence is served by the `php` binary in a process of its own, under the recipe exactly as the oracle is, and held by the same rule. The binary is `php`, `sapi/cli`'s host (ADR-0008) as every other lane builds it (revision 85), which the lane builds with cargo at the run's first such fence; a request of it records what it entered only where `PHP_WITNESS_TRACE` is set, so the binary the phpt lane runs and the one this fence is served by are one build. Coverage is observed as for any fence (§4.5 condition 2, revision 58): every request the binary serves appends the natives it entered to the file `PHP_WITNESS_TRACE` names, a forked child's request its own beside its parent's, and the lane reads them as it reads the linked engine's. The mark is on the fence and not on the crate, because posix's and the engine's fences are mostly of the other kind; every fence of `ext/pcntl` carries it. What kept the harness unforked was that the linked engine did not carry `pcntl`; since revision 84 the linked engine is `php-linked`, a process of its own that carries it, so a fence that forks and is not marked forks that process and never the harness, and the linked runner's special case for a child coming back into the lane (#1054) is gone.

## 10. Maintenance layer: keeping the harness honest

**Rule 1: a ledger row for every repeated failure.** The design's ledger gains a "From this engine" table, Keep/Reject shape, one row when a sensor catches the same class of agent mistake twice; the evidence column is a query over the log. The consequence is a change to a guide or a sensor, in HE's order: a type or visibility change first, then a manifest rule with a `reason`, then a hook, and last a sentence in the map.

**Rule 2: ADRs stay reversals**, and reach the agent at the moment they matter: every manifest rule that an ADR decided carries the number, and every failure text prints it.

**Rule 3: the revision is a harness change.** Each revision of the design of record lists what the manifest, the registry, the instruments or the locks gain or lose, and the commit that lands it. From revision 3 that section is checkable: the manifest diff in the same commit is the list.

**Rule 4: the map is regenerated, not edited.** `computed check` in CI over `AGENTS.md`, `ext/AGENTS.md`, `data/INDEX.md`, `docs/divergence.md`; a hand edit into a region body is refused at pre-commit (CM ADR 0005) and denied at the tool call by `permit`'s region check.

**Rule 5: the oracle pin is a human decision with a nightly sensor.** `oracle.toml` is the only statement of the pin; the drift job re-runs witnesses against the installed php; an agent reports drift and never moves the pin. Design documents cite the file and never the number (§14).

**Rule 6: a denial that repeats is a ledger row.** `status --section permits` at the weekly bar; a rule that fired repeatedly across sessions gets a row under rule 1; a rule that never fired in two weeks is either respected or silent, and its fixture says which.

**Rule 7: one living document per subject.** This note is one file at its current state with a ledger on top; a revision edits the sections it changes and adds one ledger entry with what changed, why, and the check. Git is the dated record. The `research/harness-research.rN.md` files are the record of the two revisions before the rule and are not edited. §14 asks the design of record to take the same shape.

## 11. Division of labour

**Human-only.** What the harness's own three files say: the oracle pin and its recipes (`oracle.toml`); every ceiling, edge, `unsafe` home, forbidden type and rule of `seams.toml`; every reason on a divergence and every flip of a row to `accepted` (`docs/divergence.toml`). A person's hand as well as a person's decision is what any change to something one of them already carries takes — one changed ceiling, one widened edge, one dropped rule, one reworded reason — that being the half of a write which can lower the bar the work is measured against. `permit` denies the agent the `Edit` and the `Write` on all three, and that does not change; what a person has settled and an agent may then type is the addition, below. ADRs, and what a revision of the design of record says; the deletion-test arguments. The wording is a person's only where the decision is unsettled: a sentence a person has settled on a ticket is an agent's to land, with the ledger row and the ticket named in the commit. `.claude/skills/**` is exempt from `harness.self` (#626); the rest of `.claude/**`, the hook JSON and the plugin manifest stay a person's. Reviewing witness diffs after `--accept`. Sign-off on a perf claim, with the A/A control read by a person, the second half of a `bench` reading (§4.2). Licence decisions. Applying the cut order when a weekly bar is missed. `computed trust` once per checkout and once over its worktrees' directory. `computed run --force`. Charting a track at the next row of design §11, `/frontier chart <track> <days>`, and closing a ticket `/frontier work <track>` ruled past the row's destination. Answering a question the design of record is silent on, and the revision or ADR that then states it. Enabling the function hook (`CLAUDE_CODE_ENABLE_FUNCTION_HOOKS` in `.claude/settings.json`, the `functionHook` option, the workspace trust dialog). Reading `status --section permits` and writing the ledger row. Choosing which prose becomes a region.

**Agent-default.** Running the protocol's paired reps against the A/A control for a `bench` reading and writing it, the measurement stated and the conclusion left to the sign-off (§4.2). The run is the agent's and the claim on the number is a person's, so a criterion that wants one is two boxes, the reading an agent produces and the sign-off a person gives, and never one box that is both: a criterion phrased "measured under the protocol, and the reading is a person's to sign off" names nothing an agent can run and closes for nobody (#128). Porting bodies against `port-map` rows. Writing kernels and natives with witnesses; running `--accept`; adding the lock line in the same commit. Running `xtask done` before proposing a change and the per-crate subsets it names. Regenerating the extension template with `new-ext`. Running `computed run` on a stale region and re-staging. Proposing a manifest rule or a divergence row in a commit message or a PR description, never in the file, which is what an agent does while nothing is settled. Landing one that is settled: a row a person has ruled on a ticket reaches `seams.toml`, `oracle.toml` or the registry through `cargo xtask steer <file> --from <proposal>`, the sanctioned writer of the three, which applies a proposal only where it adds — every value the tracked file carries must stand unchanged in the proposal, at the path and in the order it stood in, or nothing is written and the path that would have moved is named. A key a table or an array-of-tables row does not carry is an addition like a whole row is, so `porting = true` on `[[crate]]` `ext/standard` lands the way `[regime.dump]` landed (#387, ledger 51); what that widens, an `exempt` on a rule that denies the agent among it, is named in the reading, in what the instrument prints and in the commit's diff, which is how a person reads about it in the same commit. Both halves are measured: #152 is the addition, the `[regime.dump]` block the maintainer settled on the ticket, labelled `ready-for-agent`, and an agent landed; #160 is the change beside it, the `xtask` ceiling from 14000 to 18000 by a person's hand, `steer` refusing a value the row already carried. An addition through the instrument, a change by hand. The judgement is at the write and not in the label, and stays there: `ticket read` holds a criterion naming one of the three to a note that says which instrument writes it, not to a refusal, and still fails a criterion naming a denied path no instrument writes at all (#153). Whether a row adds or changes is read from the file it would replace, exactly, and a criterion's prose cannot say it; a heuristic guessing would refuse tickets an agent can in fact work, which is the failure #153 exists to stop. Proposing a rule's fixture with the rule. Working a track's frontier: filing a batch from the chart with `/frontier work <track>`, putting a decision ticket to the sources with `/grill-design` and closing it on what they say, filing the `for-a-person` ticket a silent question makes. Closing a chart sheet the cap has filled, with the comment naming the sheet that continues it: a sheet carries no acceptance criteria, so `ticket.close` does not judge its close (`exempt_label`, ledger 53), while a ticket's close is still the instrument's alone.

**Shared, with the sensor as arbiter.** Interface growth: the agent adds the lock line, the person reviews the lock diff. The manifest: the agent proposes, the person commits, `cargo test -p xtask` and the fixtures arbitrate.

**On a track, the design of record answers.** A decision ticket is a question a build ticket waits on, and on an unattended track nobody sits at the table to answer it, so the sources are asked in a person's place: `/grill-design <n>` works the ticket's question tree in rounds and puts each question, in order, to the three design documents, then the ADRs under `docs/adr/`, then php-src at the tag `oracle.toml` pins, the first that decides it answering it. A resolution is a passage with the citation that names it, `third-engine-design.md §5.6`, `ADR-0006`, `Zend/zend_vm_def.h:1234 at php-8.5.9`, recorded on the ticket and closing it; the session's own preference lives in the recommendation beside the question and nowhere else, and where the two differ the passage is what is recorded. A source is silent when no passage decides the question as asked, when this document or the design marks the point open itself (§13) or when two sources disagree, since which one moves is a person's call. A silent question is a person's: it is filed `for-a-person`, naming the sentence the design needs and the section it belongs in, and wired to block the decision ticket and every build ticket under it, so that none of them sits in the frontier `track next` reads and the decision ticket is left open. An autonomous track therefore stalls on a person and never decides for one; that ending is the edge of autonomy, not a turn that failed. The sentence itself is written into the design by a person, a revision being this list's first paragraph.

## 13. Open questions and things not verified

**D.1 to D.6, D.8 to D.15** of the earlier revisions stand as written there; the ones that matter for this revision are D.2 (where the clippy list lives; now generated, so the answer is the manifest's), D.3 (rustdoc and the `expect` fence: answered by measurement, the `=` on the fence line trips `rustdoc::invalid_codeblock_attributes` under `-D warnings` while the doctests still run, so the crates that carry witnesses allow that lint at their root, design §8), D.5 (the engine binary under `run-tests.php`, a lane control until the CLI flags exist), and D.10 (what in Function Hooks is stable; now only the fifteen-line adapter depends on it).

**D.7, settled.** Every check is an `xtask` subcommand. The shipped command hooks and pre-commit are the whole local harness in month one. The function hook is one optional adapter.

**D.16 The hook JSON shapes, answered.** Exercised on Claude Code 2.1.263 with a headless run (`data/pre-day-1.md` §4). PreToolUse stdin carries `session_id`, `transcript_path`, `cwd`, `prompt_id`, `permission_mode`, `hook_event_name`, `tool_name`, `tool_input` and `tool_use_id`; Stop stdin carries the same head plus `stop_hook_active` and `last_assistant_message`. A deny is `{"hookSpecificOutput":{"hookEventName":"PreToolUse","permissionDecision":"deny","permissionDecisionReason":"<text>"}}` on stdout with exit 0: the tool never ran and the model saw the text. A hold at Stop is `{"decision":"block","reason":"<text>"}`: the model continued on the reason and the hook fired again with `stop_hook_active` true, on which `done --hook` must pass. Day 1 runs `permit` against these recorded shapes as fixtures.

**D.17 `$.process.run` and stdin, answered.** The function-hook noun takes `stdin` (`ProcessRunInit` in the declarations `/plugin-types` writes), so the adapter passes the event on stdin, the shape the command hook reads, and no argument-length limit bounds a `Write`; `permit --json` stays for a caller with the call in hand. The test `a_large_write_on_stdin_is_judged_whole` judges a `Write` of over three megabytes whose lock sits at the end of the file (revision 10).

**D.18 The tree hash as freshness.** `git rev-parse HEAD:<path>` gives a tree hash of committed content only; for the working tree `done` must hash the crate's files itself. A content hash over the crate's sources in byte-order sorted path order, the `computed` snapshot shape (CM-spec:100), is what `tree` holds. Cost: the same as `computed check` over the same inputs, seconds.

**D.20 The runner has the tree and not the binary.** The pin names one php, a macOS keg, and the ubuntu runner cannot have it, so `XTASK_PROMISED` promises the tree alone in CI and every test that spawns the oracle skips there. Whether the pin should name a php per platform, each with its digest, so the witness lane and the runner control run in CI too, is open; what would settle it is a second `[oracle]` entry the oracle module selects by platform, with the drift lane holding both digests. Until then a witness reading is taken on the maintainer's machine.

**D.19 `parking_lot::*` in `deny_types`.** `clippy::disallowed-types` matches fully qualified paths, so a wildcard is not a clippy feature; the generator expands the manifest's wildcard into the paths the lock packages actually contain, read from `Cargo.lock`. Unverified that the expansion is complete for a crate that re-exports a lock under another name; the `permit` regex and the review of `api.lock` are the twins.
