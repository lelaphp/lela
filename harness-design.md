# The harness for the third engine: design

This is the design of record for the harness. It is one living document: every section is at its current value, and the ledger in §1 records each revision with what changed, why, and the check that would show it wrong. Git holds the dated versions. `research/harness-research.r1.md` and `research/harness-research.r2.md` are the two earlier revisions, kept unedited as records; they are not read for anything this file marks current, and the "highest `N` wins" naming rule no longer applies to this note. Design of record for the engine: `third-engine-design.md`, one living document with a ledger on top, with `jit-design.md` for the compiled tier in the same shape; the `rN` files are records and are not read for anything current. Vocabulary: `CONTEXT.md`. Decisions: `docs/adr/0001` to `0006`. Architecture terms (module, interface, seam, adapter, depth, leverage, locality) are the `codebase-design` vocabulary.

**Question.** What should a harness, in Böckeler's sense, look like for the development and maintenance of the third engine, and how much of it does the design already prescribe? And, from revision 3 on: what shape does the harness itself have to be so that it does not drift the way the design revisions have already begun to?

**Sources.** The full citation lists are in `research/harness-research.r1.md` ("Sources") and `research/harness-research.r2.md` ("Sources"); this file cites them by the same short names (**HE**, **CE**, **Sensors**, **OpenAI**, **Stripe**, **Anthropic**, **Approved**, **CM** for `computed`, **FH-dts**, **FH-issue**, **Hooks-ref**, **Plugins-ref**). ## 0. The one-paragraph design

**One manifest, one reading, one comparison, one judge, one status.** The rules of the harness live in one tracked data file, `seams.toml`, and every rule sensor is derived from it. Every instrument ends by writing one reading of one shape to `target/harness/`, and everything an agent or a person reads about the state of the engine is a rendering of those readings by `xtask status`. Every comparison against the oracle crosses one seam in the oracle module, which owns the one table of accepted differences. The edit-time gate is one instrument, `xtask permit`, and both kinds of Claude Code hook are thin adapters over it; the definition of done is one instrument, `xtask done`, called by the Stop hook, by pre-push and by CI. The harness note is one living document, and it asks the design of record to become one too.

## 2. Vocabulary

From HE: a **harness** is everything in an agent except the model, narrowed here to the part a team adds around a product it did not build; a **guide** is a feedforward control that steers before the agent acts; a **sensor** is a feedback control that observes after; **computational** controls are deterministic and fast, **inferential** ones are model-run and slower; **keep quality left** distributes checks by cost, speed and criticality; the **steering loop** is the human iterating on the harness whenever an issue repeats. The full reading of the article, its principles and the claims it attributes to others is `research/harness-research.r1.md` Part A and is not repeated.

From this design: an **instrument** is one `xtask` subcommand that measures or judges something and writes a reading; the **seam manifest** is `seams.toml`; a **reading** is the one-shaped result an instrument writes; a **divergence** is one accepted difference from the oracle, a row in the registry the oracle module owns; a **rendering** is what `xtask status` produces from readings and the manifest. Cadences: **at the tool call** (milliseconds, `permit`), **on save** (seconds), **pre-commit** (under a minute), **per commit** (CI, the 4-minute phpt budget sets the scale), **nightly**, **per revision**.

## 4. The harness's own modules

Five modules, each deep: a small interface, most of the harness's behaviour behind it. All live in `xtask` (budget 14k, r3 §4.1) except the manifest and the registry, which are data at the workspace root and under `docs/`.

### 4.1 The seam manifest: `seams.toml`

**Interface.** One tracked file. Readers: `api-check`, `unsafe-audit`, `budget`, `permit`, `status`, the generator of `ext/clippy.toml`, and the test that runs one negative-control fixture per rule. Writers: people, in the same commit as the design change that alters a rule; the commit that lands a revision of the design of record is the commit that changes the manifest.

**What it declares, once.** Every rule the design of record states as a sentence today. The list is the acceptance test for the format: a rule below that the format cannot carry is a design error in this section.

# An excerpt of seams.toml; the file is the statement. One key per line: TOML

Each `[[rule]]` has an `id`, a scope or a tool, one predicate, an optional `adr`, an optional `exempt` (paths the rule does not judge, in the scope's grammar; `permit` reads it for every predicate it judges, #23), and the `text` a failure prints. A tool is `Edit`, `Write` or `Bash`, the calls `permit` judges, or `Stop`, the hook event, for a rule `done --hook` reads over the reply and `permit` never judges (#32). The predicates are ten: `deny_types`, `allow`, `deny_pattern` (with an optional `unless`), `deny_argv` (with `with`), `on`, `deny`, `deny_lints`, `check` (a named `xtask` lint), `avoid_from` (a glossary file, or `{ file, section }` for one section of it alone, #63), and `generated` (a file and the rule it is rendered from). The one qualifier that is not a predicate of its own is `unless`: it names the instrument whose work the pattern describes, so that a hit that instrument left behind is that instrument's own and not the call's, judged by the instrument's reading and never by the shape of the call (§4.4). Each `[[seam]]` names its lock, and a lock with `sections` is diffed per section; each `[[crate]]` names its ceiling and nothing about `unsafe`; the `unsafe` homes are one rule and appear nowhere else in the file. That is the whole grammar, and `xtask` refuses a manifest with an unknown key.

Two tables beside the rules. `[telemetry]` carries the sensor telemetry's one number, `silent_days` (§7); it is optional, and while it is absent `status` renders no silent column and says which key is unset, since a default in code would be a copy. Each `[[week]]` is one exit bar of the thirty days (design §11): `days` as the table writes them, `text` in the design's words, and `reads`, the readings the bar is measured by, each the latest of an `instrument` over a `scope`, held on status pass or, with `number`, within `min` and `max`. A read names an instrument `xtask` has, so a row cannot arrive before the instrument whose reading it reads: the instrument ships its row, in the commit that fixes the number's name, and until then `status --section week` says "no reading" for the bar.

**What is derived.**

- `api-check` reads `[[seam]]` and `[[edge]]`: it regenerates each lock from the compiled crate's public items (`lock_from` says which crate for `api.lock`, r4 §4.5), the harness's own included (the `harness` seam, `xtask/xtask.lock`, whose consumers are none: nothing in the workspace imports `xtask`), fails on a diff, tags the seam's reading with the `<lock>-line` rule the manifest carries for it (`api.lock-line`, `xtask.lock-line`), fails a manifest edge not in `[[edge]]`, fails a `use` path crossing a seam, checks the bundle order is topological, prints each extension's `pub` beyond `extension()`, and treats `allowlist = true` as "the consumer may import only what the lock names" (r7 §4.2).
- `unsafe-audit` reads `unsafe.homes`. `budget` reads `[budget]` and every `[[crate]]`.
- `ext/clippy.toml` is generated from `ext.no-locks`, `reason` strings included, and committed; a stale copy is a `budget` failure (the same rule as generated code, r1 §3 principle 7, applied to a config file). Clippy finds it by nearest-file search, so it covers every `ext/<name>` and nothing under `crates/` (revision 1 D.2).
- `permit` reads every `[[rule]]` with a `tool` or a `scope` (§4.4).
- `status --section rules` renders the rule list with its ADR numbers; that rendering is the map's item 7 (§5).
- One fixture per `[[rule]]` under `xtask/fixtures/rules/<id>/` that must fail, run by `cargo test -p xtask`; a rule without a fixture fails the test. This is Mahout's "a new instrument ships with its negative control" (r1 §2.1) as a structural fact.

**The deletion test.** Delete the manifest and every number and edge reappears in six places: `api-check`'s source, `unsafe-audit`'s source, `budget`'s source, `ext/clippy.toml`, the hook's rules, and the map. That is what the inventory found had already happened in the design revisions.

**What is not in it.** The oracle pin (`oracle.toml`, a human decision with its own nightly sensor, §10 rule 5). Divergences (`docs/divergence.toml`, §4.3). Anything decided in prose: the deletion-test arguments, the ledger, the principles.

### 4.2 The reading and its store

**Interface.** Every instrument ends by writing one reading; every rendering reads them; nothing else touches the store. One shape:

```toml
instrument = "witness"                     # api-check | permit | done | track-work | ticket | budget | clippy | phpt | port-map | compile-identity | unsafe-audit | steer | divergence-reason | witness | vocab, the subcommands that write one, in cli order; bench | crosscheck | fuzz | mutants are named here and not built yet
scope = "ext/pcre"                         # a crate, a corpus subset, a gate id, or "workspace"
rule = "witness.coverage"                  # a manifest rule id when one applies
status = "fail"                            # pass | fail | skip
numbers = { run = 212, failed = 3, missing = 1 }
message = "ext/pcre: 3 witnesses differ from the oracle; preg_replace_callback lacks a witness"
adr = ""                                   # from the manifest when the rule names one
tree = "9f3c…"                             # git tree hash of the scope's sources at the time
commit = "0b62ae0"
at = 2026-09-07T01:05:49Z
session = ""                               # the hook's session_id on a permit reading; empty elsewhere
```

**Store.** `target/harness/<instrument>/<scope>.toml`, one file per key, overwritten on each run; and `target/harness/log.jsonl`, append-only, one line per reading. CI uploads the directory as the run's artefact and nothing else. The `tree` field is what makes a reading fresh or stale without a turn counter: a reading is fresh for a scope when the scope's tree hash still matches.

**Readers.** `status` (§4.6), `done` (§4.5), the steering ledger (§10 rule 6), the CI summary that answers HE's "which sensor never fails" (§7). `permit` writes a reading per denial, which is the steering-loop capture of revision 2 without `$.store` or a second file.

`session` is what makes "this session" of §4.6 a rendering rather than a guess: `permit` copies the hook's `session_id` onto every reading it writes, and `status` counts denials per session from the log.

**A bench reading's two halves.** `bench` is the instrument whose reading is not the whole answer, so its halves are named here and not inferred again at each bar. The agent's half is the run, and it is an ordinary instrument: `bench` measures the scope under the protocol this engine inherits — paired reps, the A/A control, status labels, load average recorded (`docs/perf/measurement-protocol.md`; third-engine-design.md §9) — and ends as every instrument ends, in one reading, scoped by the gate id or the bar's name, the measurement in `numbers` and `status` pass or fail against the bar. Its exit is 0 whatever the reading says, which is what `permit --bench` already turns on: a bench number is a claim a person reads with the A/A control (§4.4; revision 16, #61), so the agent states the measurement and never the conclusion (`AGENTS.md`). The person's half is the sign-off: reading the number beside its control and saying what it means — the perf claim itself, the revisit a missed G1 asks of `jit-design.md` §3, the cut order a missed weekly bar applies (§11). An acceptance criterion that wants both is therefore two boxes and not one: "a fresh passing `bench` reading at G1" is an agent's and is measured under the protocol, "the number signed off" is a person's, and a single box phrased as both can be ticked by neither.

**The deletion test.** Delete the store and nine channels reappear: `jq .summary phpt-last.json`, `jq` over the mutants outcomes, `wc -l` over the locks, `grep -c` over the divergence table, the `context` note, `harness-turn.json`, the `$.store` counters, `harness-steering.jsonl`, and a per-gate CI line. Revision 2 had all nine.

### 4.3 The oracle module owns the comparison and the divergence registry

**Interface.** One handle and four functions on it, plus the comparison pair. `Pin::oracle()` returns the oracle for one run: it asserts the pinned binary's digest once, before the first program, and refuses the whole run on a mismatch, so a lane that runs a thousand snippets hashes the binary once (revision 16). On it, `run` is revision 1's: run this program, SKIPIF or `-r` snippet under the harness regime and return normalised output (r3 §8); `run_under(invocation)` is `run` with the binary named rather than assumed, so a lane that measures the engine runs it under the one recipe and the two are comparable. An `Invocation` names the run, the binary and the program, and carries seven things over the recipe: five that a `.phpt` section adds, the ini after the recipe's, the arguments after the program, environment entries over the recipe's, what the program reads on stdin, and whether the second stream is the first; and two that no section gives, the `[regime.<name>]` of the pin whose ini stands between the recipe's and the test's, and the flags before the program, where php takes a mode of its own rather than a setting. `-l`, which compiles a program and does not run it, is the compile-identity lane's (#101), so that a corpus written to be run is compiled and never run to measure the compiler. The flag is on the invocation and not in the pin's `[regime.dump]` (#111): a regime is ini, `-d` after `-n`, and `-l` is not ini; the pin is a person's file with its own review (§11), so a lane that wants a mode of php would wait on a person for each; and `run_under` puts the same flags before the program for the binary under test as for the oracle, which is what leaves the compiler as the only difference between two dumps. Whether php prints its op arrays is the regime, and whether the program then runs is the flag. `oracle::normalise(rules, bytes)` is the recipe's CRLF and trim rule alone, which a stream and a `.phpt` expectation both go through, the stream then also losing its scratch prefix. The module also owns what every lane needs of the pin and nothing else does: the runner, which says whether a lane ran the engine, a control or nothing because the binary is absent; `Source::tree()`, the one answer to where the pinned php-src tree is: the directory `TEST_PHP_SRCDIR` names when it is set, upstream's own variable, and the pin's `[source].path` otherwise, which is the tree on the machine the pin was written on (#36); a test that would skip for a fact of the pin this machine has not, the tree or the binary, fails instead where the machine promised it through `XTASK_PROMISED`, naming what it looked for (#38), so a broken provisioning is a red test and never a quiet skip; and the expectation grammar (`--EXPECT--`, `--EXPECTF--`, `--EXPECTREGEX--`) a `.phpt` and a witness fence share. `oracle::compare(id, expected, actual) -> Verdict`, where `id` is a divergence key and `Verdict` is `Same`, `Diverged(Divergence)` when the registry has an accepted row for the id, or `Differs(diff)`. Every instrument that holds the engine to the oracle calls `compare` and never diffs on its own: witnesses (id `witness:<hash>`), phpt verdicts and the nightly runner control (id `phpt:<path>`, kinds `phpt` and `runner`), compile identity (id `compile:<path>`), the trace dump diff (id `trace:<site>`), and the differential fuzzer, whose minimised failure is proposed as a row with status `open`.

**The tally.** The phpt and witness lanes, and the compile-identity lane when it comes, share one tally (`tally::Tally<J>`): it owns the runner ladder (a control is a skip and not a reading of the engine, an absent binary is a skip, the engine is pass or fail), the rule that nothing run is not a green reading, the print loop over every non-pass item and the reading it writes; a lane contributes its judgement variants and how to judge one item, and nothing else (revision 16). A `lane` is a scheduled run of a corpus (§7), never the tally.

**The registry.** `docs/divergence.toml`, one row shape:

```toml
[[divergence]]
id = "trace:nested-entry-return"
kind = "trace"                             # witness | phpt | runner | compile | trace
reason = "A trace rooted at the entry frame of a nested execute stops with Return one opline earlier than php's (jit-design.r3 §4.2)."
status = "accepted"                        # open | accepted | fixed
since = "2026-09-06"
```

The two rows the JIT note carries in prose and the runner disagreements revision 4 §12 allows in the first weeks are rows here, so the day-30 target (< 20 rows, r1 §8.5) counts every kind, and the "target zero" of the runner control is the count of kind `runner`. A Markdown rendering for people is a computed region in `docs/divergence.md` whose command is `xtask status --section divergence`; the region is the view, the TOML is the truth (CM-spec:3).

`oracle::verdict(registry, id, met, expected, actual)` is `compare` with the caller's match standing where byte equality stands, for an expectation that is a pattern rather than bytes (`--EXPECTF--`, `--EXPECTREGEX--`); `compare` is `verdict` with `expected == actual`, so one place decides what the registry means and the count of comparisons that consult it is still one.

**What the recipe's environment is.** The pin's `[recipe.env]` is the witness regime's: `TEST_PHP_EXECUTABLE` there names the pinned oracle, which is what a witness runs. A phpt lane runs a different binary, and the corpus spawns the binary under test by that name and by `TEST_PHP_EXECUTABLE_ESCAPED`, so the runner sets both over the recipe's and under the test's own `--ENV--`. The pin does not move for this: its value is right for the regime it states.

**Who writes a row.** A person, with a reason (§11). The fuzzer and `compare` may add a row with status `open` and an empty reason; `done` fails while an `open` row touches the scope.

**The deletion test.** Delete `compare` and four instruments each decide alone whether a difference is accepted and against which list; three lists existed.

### 4.4 `xtask permit`: the judge at the tool call

**Interface.** Input: one intended tool call, as the JSON the shipped hook receives on stdin (`tool_name`, `tool_input` with `file_path`, `old_string`, `new_string`, `content` or `command`). Output: the hook's JSON, either `{"hookSpecificOutput":{"permissionDecision":"deny","permissionDecisionReason":"<text> (ADR-0005)"}}` or allow with `additionalContext` carrying the notes; exit 0 whatever it decides, since the decision is in the JSON (Hooks-ref, PreToolUse decision control). The one non-zero exit is the refusal to decide at all: a build whose compiled digest of what it judges by is not the tree's, or one that cannot read the manifest (revision 13). Every denial, every note and every refusal is a reading with `instrument = "permit"` and the rule id.

**Implementation.** The `[[rule]]` rows of the manifest with a `tool` or a `scope`, evaluated in order: the region-body rule of revision 2 (an `Edit` whose `old_string` lies in a computed region body, CM ADR 0005), `witness.exit-authored`, `unsafe.homes`, `ext.no-locks`, `api.lock-line` as a note, `git.no-verify`, `lanes.nightly`, `computed.force`, `harness.self`. Argument parsing for `Bash` is conservative, splitting on unquoted whitespace and `;`, `&&`, `|`; pre-commit remains the sensor of record for what a shell can hide. Path to crate is one function over the manifest's `[[crate]]` rows.

**What an `unless` permits.** A `deny_pattern` row that names an instrument (§4.1) refuses an authored line and not the line itself, so the judge needs evidence of whose hand wrote it, and the evidence is the instrument's reading and the tree it is stamped with (§4.2, §13 D.18). A hit is that instrument's own, and permitted, when every match already stands in the file as the instrument last saw it: each match in what the call would write is in the file on disk, the file lies in a crate the manifest names, and that crate has a reading of the named instrument whose stamp is the crate's tree hash now. `witness --accept` writes the fence line and constructs its reading after, so the line it captured is inside the tree the reading is over. A hit no such reading covers is denied whatever the store holds. That is where an authored line is refused — at the call, before what it would write is in any tree — and equally where a line a hand left in the tree is refused, by `permit --diff`, the call pre-commit makes over the staged diff (§7), the crate carrying no reading of the instrument or one stamped with an older tree. Evidence the judge cannot read is no evidence: a file it cannot read, a path no `[[crate]]` row covers, a store or a git that answers with an error each leave the hit denied, where the row stood before the qualifier. The reading's own status is condition 1's to hold (§4.5) and is not read here: a failing `witness` is the instrument's to print, in its own words, and saying it again in the row's would name the wrong problem.

**Adapters, two.** The shipped command hook, always on: `PreToolUse` with matcher `Edit|Write|Bash`, command `xtask permit` reading stdin, in `harness-plugins/hooks/hooks.json`, a person's file under `harness.self`. The function hook, `harness-plugins/hooks/harness.ts`, on unless `functionHook` in the plugin's `userConfig` is set false: a `tool.call` handler on `Edit`, `Write` and `Bash` that writes the event in the command hook's stdin shape (D.16) to `$.process.run(["xtask", "permit", "--above-the-command-hook"], { stdin })`, returns `{ deny }` or `{ ...result, context }`, and calls `$.ui.invalidate("prompt.context")` after a `Bash` call that ran an instrument. It judges the call before the command hook does, and the flag says so: a denial ends the call there and is recorded there; an allow goes on to the command hook, which judges the same call and records the notes, so a note is one reading and not two. It adds nothing the command hook does not do except the invalidation and in-process latency; it fails open, and the command hook beneath it fails open, when no candidate judges at all, on `Bash` alone, a narrower hole than the module's, which is why the module may exist (revision 2 C.8 item 8; revisions 11 and 13). Each walks its candidates, every built `xtask` that stands and then `cargo run`, and takes the first that exits 0: `permit`'s exit is 0 whatever it decides, so a non-zero one is a build that never judged — one handed a flag it does not know, one that cannot read the manifest, or one whose digest of what it judges by, `seams.toml` and the `.rs` files under `xtask/src` written into the binary by `build.rs` and compared with the tree by `built` (revision 16: a swap file or a `.DS_Store` there is not a source and does not move the digest), is not the tree's — and neither adapter passes a call on that build's silence. The built two are walked in orders that are not equal, the command hook release first and the module debug first, so one stale build does not silence both layers at once, as it did on 2026-09-08. A built candidate's stderr is dropped and the cargo candidate's kept: a refusal from a binary the walk passes over is not a message for the model, and cargo closes the list, so its stderr is the one a person needs when every candidate refused (revision 16). `cargo run` closes both lists, and its build re-runs `build.rs`, so the candidate that rebuilds carries the digest of what it is about to read and a list cannot end in nothing but refusals for want of a rebuild. The command hook is two entries over that one walk: on `Edit` and `Write` a list no candidate judged ends in a deny, since a write no judge saw does not proceed, and on `Bash` the call is handed on, since an agent repairs a broken harness with `Bash` and denying all three deadlocks the repair (revision 13). A third caller is pre-commit, which runs `permit` over the staged diff as a whole.

**What the seam does not cover.** The seam is only as good as the set of tools that cross it: the matcher is `Edit`, `Write` and `Bash`, so a GitHub MCP server attached later would not be judged at all, and `xtask ticket` is the closer only for what reaches the hook. The tracker is `gh` and nothing else, no trait and no second adapter, until a second tracker exists to make a seam real (#28).

**Cost.** `cargo run -q -p xtask -- permit` after a warm build is a process start and a manifest parse, tens of milliseconds; an `xtask` binary installed by `cargo install --path xtask` is the same without cargo. The bar: p99 under 100 ms at the tool call on the developer machine, measured by `permit --bench`, a measurement and not a gate: its reading carries pass or fail against the bar and its exit is 0 whatever the reading says, since a bench number is a claim a person reads with the A/A control (AGENTS.md; revision 16, #61). If it is missed, the manifest's rules are compiled into the binary at build time and the parse goes away; the interface does not move.

**What leaves the harness.** `rules.ts` and its tests. The function hook is enabled (revision 10), so the adapter, its tracked `tsconfig.json` and the regenerated declaration file stay, and the test job holds them: it installs Claude Code at a pinned version, writes the declarations with `/plugin-types`, runs `tsc -p harness-plugins` and `claude plugin validate --strict` (revision 16, #53). The `types-version` region that would make the pin a sensed fact is postponed (#62).

**The deletion test.** Delete `permit` and the rules are evaluated twice, in Rust after the write and in TypeScript before it, on a surface whose events "may change between releases without notice" (FH-dts:1-6).

### 4.5 `xtask done`: the definition of done

**Interface.** `xtask done [--base <ref>] [--hook]` prints the conditions of done that are unmet for the changes since `--base` (default: the merge base with the branch's track, the longest existing branch that is a proper path prefix of its name, and `main` for a branch on none), exits 1 if any, 0 if none; with `--hook` it reads the Stop hook's stdin, exits 0 when `stop_hook_active` is true, and otherwise prints `{"decision":"block","reason":"<the list>"}` (Hooks-ref, Stop).

**The conditions**, from revision 1's map item 6, now checked rather than stated:

1. For every crate with a changed file, a fresh passing reading exists for `clippy`, `witness`, `api-check`, `budget` and `unsafe-audit`, for `phpt` on that crate's subset where the crate is in the default build, whose subsets the per-commit lane runs, and for `port-map` where the crate is the one `api.lock` lives with, `php_ext` today. A crate the manifest marks `feature =` is outside that build, its corpus is the nightly lane's, and `done` does not ask it for a reading no lane run writes (#133, §7). `port-map` is asked of that one crate and of no other, because it writes exactly one reading and that is the scope it writes it at (`port_map::home_of_the_lock`, design §4.4); asked of every touched crate it would hold each of the others to a reading nothing ever writes, so the ask is narrowed in `done::instruments_of`, where `witness` and `phpt` are narrowed already, and is not a row of `done::FRESH` on its own (#148). That crate is the one to ask because the lock is in its tree: an unmatched row is the join's failing half, what the lock carries or does not carry is what makes a row one, and a change to `api.lock` therefore stales the reading and `done` says it a turn before the per-commit lane does. The join's other input is wider than its home and this condition does not reach it: an extension declaring its first native leaves rows resolved without touching `php_ext` (design §4.4, §11), and that number is the port's schedule and no condition of done, measured by the lane per commit like any other. Fresh means the reading's `tree` matches the crate's tree hash now. One reading is met without passing, and it is the only one: the `phpt` skip the missing engine binary causes, which says the engine has no binary to run the corpus through (#132). There is none until `crates/php` reaches `serve`, so while it is absent every crate that owns a subset is unmeetable, #100's twenty `ext/` crates among them. Three ways were open — build `crates/php` and `php_sapi` far enough for the corpus to run, serve a `.phpt` in process the way `witness` serves a snippet, or excuse the skip — and the third is taken, with its cost stated rather than hidden: a crate is done with its corpus unrun, which is the price of the alternative, every extension port after #100 unmeetable from its own scope. The skip is held to its cause and not to its numbers, having none worth holding, since nothing ran at all. `engine_absent` on the reading is how the lane says the binary is what stopped it and not that the subset was empty, which it alone can tell from a subset of a crate not yet created and from one whose every test skipped; `failed`, `diverged` and `borked` are zero beside it, so nothing the lane did read counted against the crate. `witness` had a rung of the same shape while the binary was why its reading was a skip, held to its numbers, something run and nothing failed or missing (#106), and has none now: the linked engine serves every snippet in this process, so its reading is a pass or a fail on its own merits (#119). This one goes away by itself when the binary exists.
2. Every kernel or native added in the diff has a witness (the `witness` reading's `missing` is zero for the crate).
3. If a `.lock` differs from its regenerated form, the lock file is in the diff (the `api-check` reading, plus `git diff --name-only`).
4. No `open` divergence touches a changed scope.
5. `permit` over the diff denies nothing.
6. `seams.toml` and `docs/divergence.toml` are unchanged in the diff, or the diff is by a person (the hook cannot tell, so the Stop hook reports it as a note, and pre-push, run by the person, passes).
7. The ticket the branch records (`branch.<name>.ticket`, the record `xtask worktree add --ticket` writes) has no unticked acceptance box, read from the `ticket` reading over its number and never from the tracker (#31). A ticket has no tree of its own, so the reading is stamped over the workspace and is fresh while the workspace's tree hash still matches: every write after the read stales it, the ones an instrument makes included, so on a branch with a ticket `xtask ticket read` is the last act of a turn that wrote anything, one tracker call per such turn, outside the hook. `done` itself is computed from git and the store alone and reaches the tracker nowhere, the Stop hook included. What this does not catch, accepted: a body edited at the tracker while the work stands still is a green `done` until the next edit of the work. A ticket with no box at all is held, since it cannot be shown done; a close the tracker refused with every box ticked is met, the boxes being the condition and not the close. A branch that records no ticket, and a detached `HEAD`, are not asked and nothing here says the word, the way `xtask` is not asked for a witness. In practice this is the Stop hook's and pre-push's condition: the record is the clone's own configuration, which a push does not carry, and a pull request's checkout is detached, so CI's `done` is not asked.

**Callers, three.** The Stop command hook, pre-push, and CI per commit. One instrument, one list; an agent and a person are told the same thing. A caller passes a base only where it knows one the branch cannot say: the Stop hook passes nothing and gets the track off the branch it stands on, pre-push passes the remote's sha per ref, and CI passes the ref a pull request targets, its checkout being a detached merge commit that is on no branch and so on no track, and nothing on a push.

**The reply, at the Stop alone.** With `--hook`, `done` also reads `last_assistant_message` for a session the store says closed a ticket (a `ticket` reading of a close carrying the hook's session), and holds the turn once when a sentence of it matches the `deny_pattern` of a `[[rule]]` with `tool = "Stop"`, the sentences named and a reading of `done` over the rule written. A sentence naming a ticket other than the one closed does not fire. This one is a heuristic beside the structural conditions on the close: a false positive costs one turn, since the second Stop passes and the recovery is to file the ticket and stop again; a false negative is the state before it (#32).

**The deletion test.** Delete `done` and the definition is seven sentences in the map plus a file protocol between `turn.step` and `stop-gate.sh` that checked one of them and only inside Claude Code.

### 4.6 `xtask status`: the one renderer

**Interface.** `xtask status --section <name> [--format md|json] [--week N] [--session]`. Fifteen sections, the set `cli::Section` accepts: `rules` (the manifest's rules, each with its ADR number, the predicate that judges it and the text its failure prints), `locks` (each lock's width against `api_items`), `budget` (each crate against its ceiling), `divergence` (the registry, with counts by kind and status), `phpt` (the corpus readings, one row per subset), `witness` (the witness readings, one row per crate), `mutants` (the mutants readings, one row per crate), `port-map` (the census joined to `api.lock`, with the rows the port has not taken yet, #98), `ticket` (one row per ticket read or closed: its criteria, the ticked and the unticked, what closed it and the session, #28), `track` (the last run of `xtask track work`, one row per ticket it worked with the outcome and the commit that ticket's branch is at, and the run's own row last, #117), `permits` (denials by rule across sessions from the log, per session and in total, with `--session-id` naming this session; then the log per instrument with the candidates for silent, §7), `week` (the weekly exit bar table with pass/fail per row from the readings, r1 §11), `git` (log and status, volatile), `bundle` (one row per crate the manifest gives an `order`, against the `api-check` reading that held the registration order to the crate graph; `ext/AGENTS.md`'s `bundle-order` region is this section, §5), `oracle` (the pin as this machine has it: the tree's variable by name and whether it is set, the pin's path, and which of the two the tree was found at; the one statement of the variable's name outside the code, which the lane reads to set the variable under the name the harness answers, so the workflow spells it nowhere, #36). `--session` prints the map file and the local facts in one block for the function hook's `prompt.context`, takes the session's id from `--session-id` or the hook's stdin head, and appends this session's denials after the local facts, nothing when it has none; the local file's `permits` region stays without it, since `computed run` has no session to hand `status`.

It reads the manifest, the registry and the store and computes nothing else. A section that needs a command of its own is a missing instrument, not a shell one-liner in a region.

**A track's worktrees.** A track runs an agent per worktree on a branch off its track branch, and a fresh worktree is bootstrapped by `xtask worktree add <branch>` rather than by a bare `git worktree add` (revision 16; revision 15 had it in shell). `xtask track` is what the two halves and `done` ask: which track a branch is on (§4.5's rule), the base `done` measures since, and the root that holds the track's store. `add` takes the branch off the track (`origin`'s where the repository has only that), lays the worktree at `.claude/worktrees/<branch>`, where `permit` resolves a call's workspace, and then makes three facts about it measured rather than guessed: it builds `xtask` there, so an `Edit` from the first tool call is judged by a built binary and not by a cold `cargo run` inside the hook's timeout (§12 item 8); it lays `.claude/harness.local.md` down through that build and renders it through `xtask regions`; and the `computed trust` grant it needs is the clone's, which covers every repository under the granted path (#74, §11), so it prints no trust line and waits on none. A command, not an instrument, so no reading is written; `cargo test -p xtask --test track_sync` holds it.

## 10. Maintenance layer: keeping the harness honest

**Rule 1: a ledger row for every repeated failure.** The design's ledger gains a "From this engine" table, Keep/Reject shape, one row when a sensor catches the same class of agent mistake twice; the evidence column is a `log.jsonl` query. The consequence is a change to a guide or a sensor, in HE's order: a type or visibility change first, then a manifest rule with a `reason`, then a hook, and last a sentence in the map.

**Rule 2: ADRs stay reversals**, and reach the agent at the moment they matter: every manifest rule that an ADR decided carries the number, and every failure text prints it.

**Rule 3: the revision is a harness change.** Each revision of the design of record lists what the manifest, the registry, the instruments or the locks gain or lose, and the commit that lands it. From revision 3 that section is checkable: the manifest diff in the same commit is the list.

**Rule 4: the map is regenerated, not edited.** `computed check` in CI over `AGENTS.md`, `ext/AGENTS.md`, `data/INDEX.md`, `docs/divergence.md`; a hand edit into a region body is refused at pre-commit (CM ADR 0005) and denied at the tool call by `permit`'s region check.

**Rule 5: the oracle pin is a human decision with a nightly sensor.** `oracle.toml` is the only statement of the pin; the drift job re-runs witnesses against the installed php; an agent reports drift and never moves the pin. Design documents cite the file and never the number (§14).

**Rule 6: a denial that repeats is a ledger row.** `status --section permits` at the weekly bar; a rule that fired repeatedly across sessions gets a row under rule 1; a rule that never fired in two weeks is either respected or silent, and its fixture says which.

**Rule 7: one living document per subject.** This note is one file at its current state with a ledger on top; a revision edits the sections it changes and adds one ledger entry with what changed, why, and the check. Git is the dated record. The `research/harness-research.rN.md` files are the record of the two revisions before the rule and are not edited. §14 asks the design of record to take the same shape.

## 11. Division of labour

**Human-only.** What the harness's own three files say: the oracle pin and its recipes (`oracle.toml`); every ceiling, edge, `unsafe` home, forbidden type and rule of `seams.toml`; every reason on a divergence and every flip of a row to `accepted` (`docs/divergence.toml`). A person's hand as well as a person's decision is what any change to something one of them already carries takes — one changed ceiling, one widened edge, one dropped rule, one reworded reason — that being the half of a write which can lower the bar the work is measured against. `permit` denies the agent the `Edit` and the `Write` on all three, and that does not change; what a person has settled and an agent may then type is the addition, below. ADRs, and what a revision of the design of record says; the deletion-test arguments. The wording is a person's only where the decision is unsettled: a sentence a person has settled on a ticket is an agent's to land, with the ledger row and the ticket named in the commit. Reviewing witness diffs after `--accept`. Sign-off on a perf claim, with the A/A control read by a person, the second half of a `bench` reading (§4.2). Licence decisions. Applying the cut order when a weekly bar is missed. `computed trust` once per clone; a worktree under a trusted clone is covered by the clone's grant (#74), so `worktree add` prints no trust line. `computed run --force`. Charting a track at the next row of design §11, `/frontier chart <days>`, and closing a ticket `/frontier work` ruled past the row's destination. Answering a question the design of record is silent on, and the revision or ADR that then states it. Enabling the function hook (`CLAUDE_CODE_ENABLE_FUNCTION_HOOKS` in `.claude/settings.json`, the `functionHook` option, the workspace trust dialog). Reading `status --section permits` and writing the ledger row. Choosing which prose becomes a region.

**Agent-default.** Running the protocol's paired reps against the A/A control for a `bench` reading and writing it, the measurement stated and the conclusion left to the sign-off (§4.2). The run is the agent's and the claim on the number is a person's, so a criterion that wants one is two boxes, the reading an agent produces and the sign-off a person gives, and never one box that is both: a criterion phrased "measured under the protocol, and the reading is a person's to sign off" names nothing an agent can run and closes for nobody (#128). Porting bodies against `port-map` rows. Writing kernels and natives with witnesses; running `--accept`; adding the lock line in the same commit. Running `xtask done` before proposing a change and the per-crate subsets it names. Regenerating the extension template with `new-ext`. Running `computed run` on a stale region and re-staging. Proposing a manifest rule or a divergence row in a commit message or a PR description, never in the file, which is what an agent does while nothing is settled. Landing one that is settled: a row a person has ruled on a ticket reaches `seams.toml`, `oracle.toml` or the registry through `cargo xtask steer <file> --from <proposal>`, the sanctioned writer of the three, which applies a proposal only where it adds — every table, key, value and array-of-tables row the tracked file carries must stand unchanged in the proposal, or nothing is written and the path that would have moved is named. Both halves are measured: #152 is the addition, the `[regime.dump]` block the maintainer settled on the ticket, labelled `ready-for-agent`, and an agent landed; #160 is the change beside it, the `xtask` ceiling from 14000 to 18000 by a person's hand, `steer` refusing a value the row already carried. An addition through the instrument, a change by hand. The judgement is at the write and not in the label, and stays there: `ticket read` holds a criterion naming one of the three to a note that says which instrument writes it, not to a refusal, and still fails a criterion naming a denied path no instrument writes at all (#153). Whether a row adds or changes is read from the file it would replace, exactly, and a criterion's prose cannot say it; a heuristic guessing would refuse tickets an agent can in fact work, which is the failure #153 exists to stop. Proposing a rule's fixture with the rule. Working a track's frontier: filing a batch from the chart with `/frontier work`, putting a decision ticket to the sources with `/grill-design` and closing it on what they say, filing the `for-a-person` ticket a silent question makes.

**Shared, with the sensor as arbiter.** Interface growth: the agent adds the lock line, the person reviews the lock diff. The manifest: the agent proposes, the person commits, `cargo test -p xtask` and the fixtures arbitrate.

**On a track, the design of record answers.** A decision ticket is a question a build ticket waits on, and on an unattended track nobody sits at the table to answer it, so the sources are asked in a person's place: `/grill-design <n>` works the ticket's question tree in rounds and puts each question, in order, to the three design documents, then the ADRs under `docs/adr/`, then php-src at the tag `oracle.toml` pins, the first that decides it answering it. A resolution is a passage with the citation that names it, `third-engine-design.md §5.6`, `ADR-0006`, `Zend/zend_vm_def.h:1234 at php-8.5.9`, recorded on the ticket and closing it; the session's own preference lives in the recommendation beside the question and nowhere else, and where the two differ the passage is what is recorded. A source is silent when no passage decides the question as asked, when this document or the design marks the point open itself (§13) or when two sources disagree, since which one moves is a person's call. A silent question is a person's: it is filed `for-a-person`, naming the sentence the design needs and the section it belongs in, and wired to block the decision ticket and every build ticket under it, so that none of them sits in the frontier `track next` reads and the decision ticket is left open. An autonomous track therefore stalls on a person and never decides for one; that ending is the edge of autonomy, not a turn that failed. The sentence itself is written into the design by a person, a revision being this list's first paragraph.

## 13. Open questions and things not verified

**D.1 to D.6, D.8 to D.15** of the earlier revisions stand as written there; the ones that matter for this revision are D.2 (where the clippy list lives; now generated, so the answer is the manifest's), D.3 (rustdoc and the `expect` fence: answered by measurement, the `=` on the fence line trips `rustdoc::invalid_codeblock_attributes` under `-D warnings` while the doctests still run, so the crates that carry witnesses allow that lint at their root, design §8), D.5 (the engine binary under `run-tests.php`, a lane control until the CLI flags exist), and D.10 (what in Function Hooks is stable; now only the fifteen-line adapter depends on it).

**D.7, settled.** Every check is an `xtask` subcommand. The shipped command hooks and pre-commit are the whole local harness in month one. The function hook is one optional adapter.

**D.16 The hook JSON shapes, answered.** Exercised on Claude Code 2.1.263 with a headless run (`data/pre-day-1.md` §4). PreToolUse stdin carries `session_id`, `transcript_path`, `cwd`, `prompt_id`, `permission_mode`, `hook_event_name`, `tool_name`, `tool_input` and `tool_use_id`; Stop stdin carries the same head plus `stop_hook_active` and `last_assistant_message`. A deny is `{"hookSpecificOutput":{"hookEventName":"PreToolUse","permissionDecision":"deny","permissionDecisionReason":"<text>"}}` on stdout with exit 0: the tool never ran and the model saw the text. A hold at Stop is `{"decision":"block","reason":"<text>"}`: the model continued on the reason and the hook fired again with `stop_hook_active` true, on which `done --hook` must pass. Day 1 runs `permit` against these recorded shapes as fixtures.

**D.17 `$.process.run` and stdin, answered.** The function-hook noun takes `stdin` (`ProcessRunInit` in the declarations `/plugin-types` writes), so the adapter passes the event on stdin, the shape the command hook reads, and no argument-length limit bounds a `Write`; `permit --json` stays for a caller with the call in hand. The test `a_large_write_on_stdin_is_judged_whole` judges a `Write` of over three megabytes whose lock sits at the end of the file (revision 10).

**D.18 The tree hash as freshness.** `git rev-parse HEAD:<path>` gives a tree hash of committed content only; for the working tree `done` must hash the crate's files itself. A content hash over the crate's sources in byte-order sorted path order, the `computed` snapshot shape (CM-spec:100), is what `tree` holds. Cost: the same as `computed check` over the same inputs, seconds.

**D.20 The runner has the tree and not the binary.** The pin names one php, a macOS keg, and the ubuntu runner cannot have it, so `XTASK_PROMISED` promises the tree alone in CI and every test that spawns the oracle skips there. Whether the pin should name a php per platform, each with its digest, so the witness lane and the runner control run in CI too, is open; what would settle it is a second `[oracle]` entry the oracle module selects by platform, with the drift lane holding both digests. Until then a witness reading is taken on the maintainer's machine.

**D.19 `parking_lot::*` in `deny_types`.** `clippy::disallowed-types` matches fully qualified paths, so a wildcard is not a clippy feature; the generator expands the manifest's wildcard into the paths the lock packages actually contain, read from `Cargo.lock`. Unverified that the expansion is complete for a crate that re-exports a lock under another name; the `permit` regex and the review of `api.lock` are the twins.
